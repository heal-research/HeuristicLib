# Layering

HeuristicLib organizes dependencies by responsibility. A higher layer may use a lower layer; lower-layer implementations must not take on higher-layer responsibilities. Types in the same layer may collaborate. Authoring contracts have one explicit signature bridge to resolution, described below. Folders and assemblies help readers find code, but neither defines the layer of a type. The planned architecture test applies these assignments to source references.

## Layers and ownership

| Layer                 | Responsibility                                                                      | Namespaces and type kinds                                                                                                                                                                                                                                                                                                   |
| --------------------- | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| L0: domain vocabulary | Values and concepts that do not need a configured execution graph.                  | Candidate and search-space values, objective values and comparison, random sources, and shared collections in `SearchSpaces`, `Objectives`, `Random` and `Collections`. The `CountAccumulator` and `DurationAccumulator` sinks belong in `Instrumentation` here.                                                            |
| L1: composition model | Contracts and validation for reusable configurations and their execution instances. | `IExecutionConfiguration`, `IExecutionInstance`, `ExecutionSignature`, configuration validation and `Observation` in `Execution`; role interfaces and authoring bases in `Algorithms` and `Operators`; problem contracts in `Problems`. `SearchSpaceCompatibility` is a composition check in `SearchSpaces`.                |
| L2: resolution        | Creation and sharing of execution instances, decorations and module installation.   | `ResolutionScope`, `ResolutionScopeBuilder`, `Decoration` and `IExecutionModule` in `Execution`.                                                                                                                                                                                                                            |
| L3: library content   | Implementations and shared execution helpers used by configurations.                | Instantiable configurations in `Algorithms`, `Operators`, `Problems` and `Encodings`; role-specific counting and duration wrappers in `Operators.*`; `ExecutionConcurrency`, `ExecutionConcurrencyKind` and `BatchExecution` in `Execution` (source folder `Execution/Concurrency`). General numerical, data and machine-learning implementations belong here when they perform library work. |
| L4: hosting           | Starting and coordinating runs and their lifecycles.                                | `AlgorithmRun`, `ExecutionStream`, `RunLifecycleState` and the internal run host in `Execution` (source folder `Execution/Runs`); experiment configurations, trials and `ExperimentRun` in `Experiments`. Hosting uses composition and resolution contracts, not concrete library algorithms.                                                                     |
| L5: analysis          | Observing runs and deriving results.                                                | Analyzers, traces, clocks, observation wrappers and analysis conveniences in `Analysis`. Analysis may use library content and attach modules to runs.                                                                                                                                                                       |

`Algorithms`, `Operators` and `Problems` intentionally contain both L1 contracts or authoring bases and L3 implementations. Classify a reference by the type it names, not solely by its namespace. For example, a run may accept `IAlgorithm<...>` but must not construct a concrete `GeneticAlgorithm<...>`. `Execution` likewise contains L1 contracts, L2 resolution types, the shared L3 concurrency helpers grouped in the `Execution/Concurrency` source folder, and L4 hosting types grouped in the `Execution/Runs` source folder. The observation record stays in `Execution`; the mechanism that installs observation callbacks belongs to `Analysis`.

The creation members of `IExecutionConfiguration<TExecutionInstance>`, algorithm and operator role contracts, and their authoring bases take a `ResolutionScope`. That L1-to-L2 type reference is the narrow bridge through which a configuration creates an instance. It does not make a configuration responsible for the resolver's cache, decoration ordering or run lifecycle. The architecture check permits these creation-signature references rather than treating every reference to `ResolutionScope` as a forbidden edge.

`HeuristicLib.Experimental` can contain content, hosting or analysis at the corresponding layers and may depend on the main library. The main library must not depend on Experimental. `HeuristicLib.PythonInterop` is an integration client above the main library and Experimental; it does not set dependencies for either one. Experimental API adapters follow the same direction.

## Dependency rules

- Hosting may depend on domain vocabulary, composition contracts and resolution. It must not reference `Analysis` or concrete library algorithms.
- Operators, algorithms and problems may use lower-layer contracts and shared helpers. Their content must not reference `Analysis`, except for the named dynamic-problem exception below.
- Objectives must not reference a concrete encoding. A comparison policy can validate dimension indices without depending on `Encodings.Permutations`.
- Analysis may reference hosting for conveniences such as attaching an analyzer to a run. The dependency points from L5 to L4; the run itself accepts execution modules without knowing analyzers.
- Resolution and run internals are used only by their owning concepts. In particular, the internal constructors and build path of `ResolutionScope`, `ResolutionScopeBuilder` and `Decoration` belong to resolution code under the `Execution` source folder, excluding its `Runs` and `Concurrency` grouping folders; internal run streaming and cancellation entry points belong to hosting code under the `Execution/Runs` and `Experiments` source folders. Sharing the `Execution` namespace does not grant hosting code access to resolution internals. Their `internal` accessibility is not permission for unrelated code in the consolidated assembly to use them.

The one planned exception is `IterationUpdateModule` in Experimental's `DynamicProblem.cs`. It uses `Analysis.Observe` to advance a dynamic problem after each iteration. This is problem control flow, and its source remains in `Problems.Dynamic` until the later aspect work replaces that observation hook. The architecture test records this exact edge rather than exempting all dynamic problems or all of Experimental.

## Layers and execution phases

Configuration and execution instance are phases within these responsibilities, not successive layers. A configuration describes a reusable graph; resolution creates run-bound execution instances from it; those instances execute. An operator authoring base belongs to the composition model even though it defines how an instance is created. A concrete operator configuration belongs to library content even though it also describes an instance. `ResolutionScope` owns instance identity and decoration while crossing from description to execution.

A run composes an algorithm, a problem, a random source and execution modules, then creates one root resolution scope for that setup. Analysis can supply a module that observes selected boundaries. The module declares its decorations before the scope resolves the execution graph; the run has no need to know the module is an analyzer.
