# Layering

HeuristicLib organizes dependencies by responsibility. A higher layer may use a lower layer; lower-layer implementations must not take on higher-layer responsibilities. Types in the same layer may collaborate. Authoring contracts have one explicit signature bridge to resolution, described below. Folders and assemblies help readers find code, but neither defines the layer of a type. The architecture test in `HeuristicLib.Tests/Architecture` checks the dependency rules below against source references.

## Layers and ownership

| Layer                 | Responsibility                                                                                | Namespaces and type kinds                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| L0: domain vocabulary | Representation-independent values and concepts that do not need a configured execution graph. | Search-space and candidate-invariant contracts in `SearchSpaces`; objective values and comparison in `Objectives`; random sources in `Random`; shared collections in `Collections`; general numerics in `Numerics`; problem contracts and abstract bases (`IProblem`, `IStochasticProblem`, `Problem` and `SingleSolutionProblem`) in `Problems`. Shared helpers without higher dependencies also belong here: the `CountAccumulator` and `DurationAccumulator` sinks in `Instrumentation`, and `ExecutionConcurrency`, `ExecutionConcurrencyKind` and `BatchExecution` in `Execution` (source folder `Execution/Concurrency`). |
| L1: composition model | Contracts and validation for reusable configurations and their execution nodes.           | `IConfigurationNode`, `IExecutionNode`, `ExecutionSignature`, configuration validation and `Observation` in `Execution`; role interfaces and authoring bases in `Algorithms` and `Operators`. `OperatorContractComposition`, `OperatorContractVerification` and `SearchSpaceCompatibility` are composition checks over operators in `SearchSpaces`.                                                                                                                                                                                                                                                                    |
| L2: resolution        | Creation and sharing of execution nodes, wrappers and module installation.             | `ResolutionScope`, `ResolutionScopeBuilder`, their internal sharing/preparation/binding collaborators, and `IExecutionModule` in `Execution`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| L3: library content   | Concrete representations, problems and configurations that implement library behavior.        | Instantiable configurations in `Algorithms` and `Operators`; candidate representations with their search spaces, operators and recommendations in `Encodings.*`; concrete problems and representation-specific problem bases, such as `RealVectorProblem`, in `Problems`; role-specific counting and duration wrappers in `Operators.*`. Data and machine-learning implementations belong here when they perform library work.                                                                                                                                                                                                  |
| L4: hosting           | Starting and coordinating runs and their lifecycles.                                          | `AlgorithmRun`, `ExecutionStream` and `RunLifecycleState` in `Execution` (source folder `Execution/Runs`); experiment configurations, trials and `ExperimentRun` in `Experiments`. Hosting uses composition and resolution contracts, not concrete library algorithms.                                                                                                                                                                                                                                                                                                                                                          |
| L5: analysis          | Observing runs and deriving results.                                                          | Analyzers, traces, clocks, observation wrappers and analysis conveniences in `Analysis`. Analysis may use library content and attach modules to runs.                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

`Algorithms` and `Operators` intentionally contain both L1 contracts or authoring bases and L3 implementations. Classify a reference by the type it names, not solely by its namespace. For example, a run may accept `IAlgorithm<...>` but must not construct a concrete `GeneticAlgorithm<...>`. `AlgorithmExtensions` in `Algorithms` is an L4 convenience: its `CreateRun` and `Stream` start runs from an algorithm, so users find them beside algorithms. `Problems` likewise contains L0 problem contracts and L3 problems, and `SearchSpaces` contains L0 vocabulary and three L1 composition checks. `Execution` contains the shared L0 concurrency helpers grouped in the `Execution/Concurrency` source folder, L1 contracts, L2 resolution types, and L4 hosting types grouped in the `Execution/Runs` source folder. The observation record stays in `Execution`; the mechanism that installs observation callbacks belongs to `Analysis`.

An encoding is a vertical slice through one candidate representation: the candidate type, its search spaces, its operators and the operators a search space recommends. Because a search space may recommend concrete operators, every type in `Encodings` is library content. Domain vocabulary stays independent of any concrete representation, and problems pinned to one representation belong to library content with it.

The common `IConfigurationNode<TExecution>` and core role contracts prepare typed execution factories whose binding callbacks take a `ResolutionScope`. That L1-to-L2 type reference is the narrow bridge through which a configuration creates an execution. It does not make a configuration responsible for the resolver's cache, wrapper ordering or run lifecycle. The architecture check permits these creation-signature references rather than treating every reference to `ResolutionScope` as a forbidden edge.

`HeuristicLib.Experimental` can contain content, hosting or analysis at the corresponding layers and may depend on the main library. The main library must not depend on Experimental. `HeuristicLib.PythonInterop` is an integration client above the main library and Experimental; it does not set dependencies for either one. Experimental API adapters follow the same direction.

## Dependency rules

The main `HeuristicLib` assembly contains both public contracts and their implementations. There is no separate Contracts assembly. The layer rules apply within that assembly; production package boundaries separate the main toolkit, Experimental features and Python integration.

- Domain vocabulary references only domain vocabulary. It does not reference a concrete encoding: a comparison policy, for example, validates dimension indices without depending on `Encodings.Permutations`.
- Hosting may depend on domain vocabulary, composition contracts and resolution. It must not reference `Analysis` or concrete library algorithms.
- Operators, algorithms and problems may use lower-layer contracts and shared helpers. Their content must not reference `Analysis`, except for the named dynamic-problem exception below.
- Analysis may reference hosting for conveniences such as attaching an analyzer to a run. The dependency points from L5 to L4; the run itself accepts execution modules without knowing analyzers.
- Resolution and run internals are used only by their owning concepts. In particular, the internal constructors and build path of `ResolutionScope` and `ResolutionScopeBuilder`, and the `ExecutionSharingScope`, `ExecutionPreparation`, `ExecutionBindings` and `WrapperRegistration` collaborators (including their nested helpers) belong to resolution code under the `Execution` source folder, excluding its `Runs` and `Concurrency` grouping folders; internal run streaming and cancellation entry points belong to hosting code under the `Execution/Runs` and `Experiments` source folders. Sharing the `Execution` namespace does not grant hosting code access to resolution internals. Their `internal` accessibility is not permission for unrelated code in the consolidated assembly to use them.

The one allowed exception is `IterationUpdateModule` in Experimental's `DynamicProblem.cs`. It uses `Analysis.Observe` to advance a dynamic problem after each iteration. This is problem control flow, and its source remains in `Problems.Dynamic` until the later aspect work replaces that observation hook. The architecture test records this exact edge rather than exempting all dynamic problems or all of Experimental.

## Layers and execution phases

Configuration and execution node are phases within these responsibilities, not successive layers. A configuration describes a reusable graph; resolution creates run-bound execution nodes from it; those executions execute. An operator authoring base belongs to the composition model even though it defines how an execution is created. A concrete operator configuration belongs to library content even though it also describes an execution. `ResolutionScope` routes the transition from description to execution through sharing, preparation and binding collaborators. Each collaborator owns its state and invariants; the public scope does not manipulate their caches.

A run composes an algorithm, a problem, a random source and execution modules, then creates one root resolution scope for that setup. Analysis can supply a module that observes selected boundaries. The module declares its wrappers before the scope resolves the execution graph; the run has no need to know the module is an analyzer.

## Run ownership

`AlgorithmRun` owns its lifecycle and retained execution enumerator together: a paused run retains the enumerator for resumption, and a running stream has exclusive access to it. `ExecutionStream` adapts synchronous and asynchronous enumeration and enforces single consumption. `ExperimentRun` owns trial scheduling and its terminal lifecycle; it rejects starting an experiment whose trial has already been started directly.

The runs share lifecycle state names but have different transition rules. Keep those rules and diagnostics with the run that owns the execution or scheduling. Extract a shared component only when it can own a concrete shared responsibility; grouping composition fields or moving state transitions behind a configurable host does not establish one.

## Concept placement

Namespaces group concepts that users work with together, even when their types belong to different layers. `SearchSpaces` keeps `IOperatorContract` beside its composition, verification and compatibility helpers. `Data` serves symbolic expression interpretation, machine learning and Python integration, so it remains independent of `MachineLearning`. `Collections` remains the home of shared collection vocabulary even with a single public type.

The main benchmark functions share `Problems.TestFunctions`; `SingleObjectives`, `ZDT` and `MetaFunctions` are grouping folders. Experimental's `Problems.TestFunctions.BBoB` is a distinct benchmark suite with different implementations, including types whose names overlap the main functions. Python integration uses the single `HEAL.HeuristicLib.PythonInterop` namespace with `SymbolicRegression`, `Experiments` and `Analysis` grouping folders. These follow the [namespace and folder rules](/contributing/developer-guidelines#§-9-5-match-namespaces-and-folders-by-audience).
