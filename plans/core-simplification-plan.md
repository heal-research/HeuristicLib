## Goal

Simplification is the primary driver. Complex behavior should follow from a small set of consistent rules, and a new scenario should first be expressed with existing systems rather than answered with a new mechanism.

These stay: the domain model, the configuration/executor split, scopes as the sharing unit, `Sharing`, run-bound results, the operation contracts with generic invocation wrappers, truly problem-specific operators, and the rule that external operations can do everything built-in operations can.

## Decisions taken on 2026-11-05

### Configurations are data

Configuration nodes are pure data records. Storing lambdas or live objects on them is against a fundamental guideline that is held very highly. It is not unbreakable: where a special case has a technical need, such as Python interoperability, a documented exception is acceptable. Allowing no delegates under any circumstances stays rejected.

Termination and interception are fundamental parts of an algorithm's configuration, so they stay in the configuration graph. Attaching them to the state stream afterwards is rejected.

### Automatic placement is substitution in the configuration graph

"Aspects" are no longer something placed somewhere and applied during resolution. A substitution is a convenience that maps one configuration graph to another with ordinary wrappers in place. It is a pure function: its result follows only from the graphs and replacements passed to it, including which references they share, and it changes nothing else. Graph rewriting is the name of the technique, and `Substitute` is the general mechanism. It may use lambdas, predicates and function objects, because they are not stored in a configuration. Its result is an ordinary configuration, which obeys the same data rule as a hand-written one. Resolution has no interception left to handle.

The idea and some terminology of aspect-oriented programming may stay in the documentation, but the implementation is a configuration-to-configuration mapping. This is where the work starts. It reopens the [automatic substitution option set aside on 2026-11-04](operator-state-lifetimes.md#advice-and-scope-layers-under-discussion-since-2026-11-04), and the form recorded under [advice expressed as wrapper configurations](developer-backlog.md#advice-expressed-as-wrapper-configurations) stays different: that recipe ran inside the resolver, while a substitution finishes before resolution starts.

### Other decisions

- **`ResolutionScope` must shrink.** It does too many things and has become a god object.
- **Introspection without reflection.** Configuration graphs become introspectable through a declared parameter system along the lines of the [parameter plan](configuration-parameters-and-experiment-persistence.md). Experiment setup should build on it.
- **String-based configuration is a separate later task.** This branch builds the foundation only. REST APIs and configuration from strings are a [backlog item](developer-backlog.md#runs-execution-and-experiments).
- **Design rules come early.** Agents should express new ideas with existing systems. See phase 0.
- **Concepts are presented deliberately.** The fundamental concepts should be clear and shown to users first.
- **`Substitute` is the general mechanism.** Analyzers and budgets use it under the hood. See [D13](#decided-in-round-5).
- **A substitution happens eagerly.** The configuration the caller holds is what runs, and there is no intent node. See [D1](#decided-in-round-1).
- **Parameters are declared by hand for now.** Reflection is avoided, and the cost of that choice gets its own detailed design once its overhead is known. See [D2](#decided-in-round-1).
- **Sequential substitutions are deterministic.** The output of the first is the input of the second. See [D3](#decided-in-round-1).
- **The adaptive mutation strength is explicit.** It is configuration; its runtime part is a plain object holding the current value, and it is given to the strategy. See [D4](#decided-in-round-1).
- **An analyzer is what an aspect was.** It is a collection of substitutions that places the hooks an analysis needs. See [D22](#decided-in-round-6).
- **`Analyzer` is the name to keep.** `Instrument` retires and keeps its name until the type is removed, and `Fits` becomes `Supports`. See [D13](#decided-in-round-2).
- **A meta-algorithm can give children another problem.** It does so while constructing their executors. See [the conditions](#problem-bound-executor-conditions).

### Substitution

```csharp
// Explicit placement stays as it is.
var calls = ga.Mutator.Invocations.Count();
var explicitly = ga with { Mutator = ga.Mutator.Counted(calls) };

// The base form: a predicate on a node and a replacement, both plain lambdas. Nothing is stored.
// The type of the lambda's parameter says which nodes are considered.
var main = ga.Substitute(
    (IOperator<Evaluation, RealVector> evaluator) => evaluator is INamedConfiguration { Name: "main" },
    evaluator => evaluator.Timed(duration));

// Common patterns: every node of a type, and one node by reference.
var timed = ga.Substitute((IOperator<Evaluation, RealVector> evaluator) => evaluator.Timed(duration));
var counted = ga.Substitute(ga.Mutator, mutator => mutator.Counted(calls));

// A replacement need not wrap anything.
var swapped = ga.Substitute(ga.Mutator, _ => new GaussianMutator(0.5, 0.1));

// There is one path: the call produces the explicit graph, so tests can compare the two by value.
Debug.Assert(explicitly == counted);

// Provisional syntax (D25): an analyzer knows its own source. The result is still a GeneticAlgorithm, because only inner slots change (see D31 for a source on the receiver itself).
var best = ga.Evaluator.Invocations.TraceBestSoFar();
var traced = ga.AnalyzedBy(best);
var run = traced.CreateRun(problem, random);
await run.CompleteAsync();
var curve = run.Result(best).Snapshot();

// A budget keeps its call site and returns the substituted graph.
var limited = ga.LimitedToInvocations(ga.Mutator, 5);
```

Selection needs no dedicated type. The type of the lambda's parameter replaces `Pointcut.OfType`, and C# expressions replace `Named`, `And`, `Or` and `Not`. Production code only selects by reference today, apart from the budgets' `OfType<IOperator>().Not()` seed, which goes with them in phase 3. This is the core version D14 asks for. Passing a reference such as `ga.Mutator` is a shortcut for matching by reference equality. It adds only the error D17 requires when nothing matches.

One small public pair remains, `Substitution`: a predicate and a replacement with the node type erased. A single call that handles different node types needs it, which D17 requires, and so do analyzers, including external ones. It replaces `Aspect`. `node.Substitute(substitutions)` is the form everything builds on, and the other overloads are shortcuts that create a `Substitution`.

Rules of a substitution:

- Several substitutions apply one after another, each seeing the result of the previous one (D28). `O` with `A` and then `O` with `B` gives `A(B(O))`, because `B` matches `O` and not `A`. A node substituted away no longer matches.
- One substitution visits each node of its input once, children first, and never revisits its own replacement.
- The predicate sees the node as the call received it, and the replacement receives that node with its children already substituted. A target is therefore still found when one of its children changed, as Roslyn's `ReplaceNodes` does it, also when an earlier substitution of the same call changed it (D17).
- A selection by type also matches wrappers from earlier substitutions, on purpose: count two mutators, and a later substitution on every counted mutator finds both. The same rule means that substituting every evaluator with `Timed` and then with `Counted` gives `Counted(Timed(Counted(E)))`, which counts twice unless the predicate excludes the wrapper. `Counted<Mutation, T>` and `Counted<Evaluation, T>` are different types, so a selection across operations takes one substitution per operation, unless D11 settles a dispatch. A counted mutator can become a timed mutator, but not a counted evaluator, which the compiler rejects.
- The receiver can match too. It counts as a slot typed by its static type, so wrapping a `GeneticAlgorithm` receiver is an error under D10, while a receiver typed `IAlgorithm<TCandidate, TSearchState>` can hold the wrapper.
- It is memoized by reference, so a reference used in two slots stays one reference. [D26](#decided-in-round-8) settles how this applies to multi-operation nodes and `Sharing` lists.
- A slot that cannot hold the replacement is reported according to [D10](#decided-in-round-3), never silently changed in type.
- It returns the same instance when nothing was selected, and can report that nothing matched. That was [given up](developer-backlog.md#detecting-observation-sources-that-never-resolve) under advice.
- Substituting within one subtree is how a caller scopes it, which also delivers [caller-path selection](developer-backlog.md#matching-and-wrapper-extensions): `Cycle(a.AnalyzedBy(trace), b)` observes only A's calls of a shared operator.

The rejected "predicate-plus-factory decorators" differ from this: they were registered in setup closures and applied during resolution, which keeps advice's rules under a new name.

Decision A of step 3 also improves: placing an instrument on inner operators keeps the concrete algorithm type, so a grid over `GeneticAlgorithm<T>` no longer loses it at an `Advised` wrapper.

### Parameters

```csharp
public sealed record TournamentSelector<TCandidate> : Selector<TCandidate>
{
    public int TournamentSize { get; init; }

    public static Parameter<TournamentSelector<TCandidate>, int> TournamentSizeParameter { get; } =
        new(nameof(TournamentSize), static selector => selector.TournamentSize, static (selector, value) => selector with { TournamentSize = value });

    public new static IReadOnlyList<IParameter> Parameters { get; } = [TournamentSizeParameter];

    public override IReadOnlyList<IParameter> GetParameters() => [.. base.GetParameters(), .. Parameters];
}
```

- Each parameter is a static member, and `Parameters` is a static collection of the record's own parameters (D24). All type names here are provisional.
- A walk calls `GetParameters()`, which adds the inherited parameters. C# cannot chain overrides by itself without reflection or a generator, so this one line does it. It cannot name a wrong base, and a record with no parameters of its own writes nothing.
- The property's type fixes the owner and the value, so target-typed `new` types the lambdas. A generic factory such as `Parameter.Setting(...)` cannot infer the owner, so that form does not compile.
- The collection comes after its members, because static initializers run in textual order. The compiler warns about the wrong order (CS8601).
- `GetParameters()` is also how a walk holding an erased node reaches the static collection without reflection. It needs its own name, because a type cannot have a static and an instance member with the same name.
- Properties stay the source of values. Metadata is per type and holds no instance data.
- The declared value type says what a walk does with a parameter, so a walk never asks what kind it is ([D41](#decided-in-round-14), [D45](#decided-in-round-15)).
- Declarations in a base record cover inherited settings, because a record's `with` keeps the runtime type.
- Delegate-valued parameters are declared as such, so a walk can report them instead of pretending to persist them.
- Executors keep typed fields. No lookup by parameter happens during execution.

### Phase 5: executor controls

Accepted (D4). See [the proposal](#executor-control-proposal). `IExecutionNode` arrives here (D19), together with the first node that does not execute anything.

Decided by the developer on 2026-11-16, while drafting the implementation spec:

- `IRunResult` derives from `IExecutionNode` instead of `IExecutor`. A run result is a runtime object created by a configuration node and held in the scope's table, which is what D19 calls an execution node, but it executes nothing.
- A shared node that links an operator and an algorithm to one runtime value has reference equality. The resolver keys by reference, so value equality would make configurations that adapt and configurations that do not compare equal, and keying by value would silently merge independently created nodes.
- **The base value stays plain data, and adaptation is a separate optional link.** This amends the proposal's "holds the current value". `GaussianMutator` keeps `double MutationStrength` as its base, a regular property with value equality, and gains a nullable reference to an adaptation node. Two mutators without an adaptation and equal bases are equal; equal bases with the same adaptation reference are equal. The base stays a declared `double` parameter. An adaptation option suggested during review let the link hold only a scale factor; the developer generalized it.
- **Adaptation is general, not specific to mutation or to the evolution strategy.** Its read side is one interface mapping the base value to the effective value (`double` to `double`), so any operator can make a parameter adaptable through an optional link. Each form is a node with its own runtime object and its own write operation. Scale (multiply) and offset (add) are the first two forms. An algorithm's slot names the form its rule writes, so the evolution strategy's 1/5 success rule takes a scale form. The working name in discussion was "strategy parameter"; the final name is open.
- The base value's adaptation is not itself a declared parameter in this phase. The baseline comes first, and fitting adaptation into the declared parameter system is later work.
- **The concept is named adaptation.** The read side is `IAdaptation`, and an abstract class `Adaptation<TAdapted>` is the base of adaptation nodes, so they are classes with reference equality and cannot be records. "Strategy parameter" was rejected because evolution strategies use it for self-adaptive values carried by each individual, and because the library's _parameter_ already means a declared configuration parameter. Scale and offset are the only forms for now; clamping, absolute override and composite forms are added when a rule needs them.

### Phase 6: simplify observation

Delivers ideas 10 and 14. Today's concepts are sources, observation records, instruments, traces, value functions, retention, clocks, counters, durations, accumulating results and `IObservationInstrument`. #### Phase 6 proposed model, drafted on 2026-11-16

This is the first draft, kept for the record. The [decisions](#phase-6-decisions) below supersede it wherever they differ: retention stays unchanged (item 5), the one-line form is provisionally `Aggregate` (D75), `IObservationInstrument<T>` becomes `IObservationAnalyzer<T>` (D77), the callback is not an `Analyzer<TResult>` (D78), and a `Share` does not narrow an analyzer's result (D84).

1. **An analyzer is a configuration node whose execution node is its result for the run.** `Analyzer<TResult> : IConfigurationNode<TResult>, ISubstitutionBundle where TResult : class, IRunResult`, abstract, in `Analysis`. Authors override `CreateExecutionNode`, which creates the empty result, and `CreateSubstitutions`, which the base class caches as `Instrument` does today. Because the result is an `IRunResult`, it is owned by the run's root and spans the run, exactly as a counter's count is, and a `Share` narrows it the same way. `Instrument`, `Instrument<TResult>`, the instrument table in `RunResults` and both `Result(Instrument<TResult>)` overloads go, leaving one `run.Result(configuration)` and one table. This is round 16's suggestion. The cost is that every result type implements the `IRunResult` marker, so a plain `Dictionary` can no longer be a result.
2. **The fold.** An analyzer creates a per-run result (the seed) and records each observation into it (the step); `Observed` places the step at a boundary. A trace, a best-so-far curve, a Pareto front, a genealogy and a callback all have this shape. Where the step lives is open (round 2). A one-line form for analyzers over one observation type removes the class: `var summary = evaluator.Invocations.Accumulate(() => new CandidateSummary<T>(), (summary, observation) => summary.Add(observation.Candidates));`. An analyzer over several observation types, such as the genealogy, stays a class.
3. **Counting and timing keep their wrappers and nodes,** because they allocate no observation and timing includes failed calls.
4. **Clocks only read.** `IClock<out TTime>` gets one public member that creates a reader for a run, so an external clock implements it directly, as `Counter` and `Duration` do; the non-generic `IClock` stays for mixed lists. `IClock` no longer extends `ISubstitutionBundle`. `Counter` and `Duration` implement both interfaces in their own right, and a trace places those of its clocks that are bundles, after its own placement as today. `Clock.Elapsed` and `EpochClock` implement only `IClock<T>`, so `AnalyzedBy(Clock.Elapsed)` no longer compiles. `Clock<TTime, TResult>` goes; a clock that observes is an analyzer that is also a clock.
5. **Retention stays a setting of the trace.** The four forms become private behind their factories; `TraceRetention` and `RetentionDecider` stay open to external retentions. The glossary folds _Trace retention_ into _Trace_ in phase 8.
6. **Idea 10.** A trace binds its clocks into a fixed column order once, and each entry stores a row of times instead of a dictionary. `TraceEntry.At(clock)` looks up the column. Internal only.
7. **Names.** The static `Analyzer` factory class stays, and `Analyzer<TResult>` is the base, as `Clock` and `Clock<,>` sit side by side today; no non-generic base is needed once results live in the scope's table. `Observing` returns an `ISubstitutionBundle`, and PythonInterop's list becomes `List<ISubstitutionBundle>`.

#### Phase 6 decisions

Decided by the developer on 2026-11-16, in the first rounds on the proposed model.

- **D64. An analyzer is a configuration node whose execution node is its result for the run, and `IRunResult` stays.** This accepts item 1 of the proposed model: `Instrument`, its table in `RunResults` and the `Result(Instrument)` overloads go, leaving one table and one `run.Result(configuration)`. The developer asked whether any execution node could be read instead, with the marker gone. It cannot, because lifetime decides which node a read means: a Cycle builds each turn in a new child scope (`CycleAlgorithm.cs:109`), so without the marker every turn would build its own empty result in a discarded scope, while with it every turn's wrapper reaches the root's one result (`SubstitutedAnalysisTests.TraceInsideACycleChild_ContinuesAcrossTurns`). Making every non-executing node run-owned instead would reverse D16's default that an unshared adaptation restarts each turn. Result types implement the marker, so a plain `Dictionary` needs a class around it. A more general way to state which lifetime a node is bound to may replace the marker later; [the backlog](developer-backlog.md#runs-execution-and-experiments) records it.
- **D65. A clock only reads.** `IClock<out TTime>` has one public member, `Func<TTime> CreateReader(RunResults results)`, so an external clock implements it directly as the built-ins do; the non-generic `IClock` stays for mixed lists, with its untyped read internal. `IClock` no longer extends `ISubstitutionBundle`. `Counter` and `Duration` implement both interfaces, and a trace places those of its clocks that are bundles, after its own placement as today. `Clock.Elapsed` and `EpochClock` implement only `IClock<T>`, so attaching them no longer compiles. `Clock<TTime, TResult>` goes; a clock that observes calls is an analyzer that is also a clock. Superseded by [D103](#phase-6-decisions-on-2026-11-18) on 2026-11-18: a clock is a configuration node whose execution node is its reading, `CreateReader` goes, and a trace places none of its clocks.
- **D66. Collecting keeps its four parts, and the update stays on the analyzer.** A source names the call, an observation wrapper sees it, the analyzer is the handle that places wrappers, creates each run's empty result and says how one observation updates it, and the result holds one run's data. The update is not moved onto the result type, which would tie domain results such as `ParetoFront` to observation types and put the search state into `GenealogyGraph` and `RankState`. A one-line form for an analyzer over one observation type replaces the three-override class, as in `evaluator.Invocations.Accumulate(() => new CandidateSummary<T>(), (summary, observation) => summary.Add(observation.Candidates))`; its name is provisional. An analyzer over several observation types stays a class. The developer finds the top-level analysis API complicated as a whole, which is discussed separately.
- **Retention is postponed.** Phase 6 leaves retention unchanged, including its public forms. The developer is not sure the retention system is right; [the backlog](developer-backlog.md#algorithms-representations-and-analysis) records the open question.
- **D67. Simple analysis is the direction phase 6 works towards.** The developer judged on 2026-11-16 that no new user would arrive at today's call site to track qualities over evaluations: a source, a separate counter, a clock list, an attach call returning a new configuration, a run created from that configuration and a result projected by a clock. The target is one object that says what to record, is passed to `CreateRun`, and is the key the result is read with:

  ```csharp
  var best = Analyzer.BestSoFar<RealVector>();      // D69
  var run = ga.CreateRun(problem, random, [best]);  // D71
  await run.CompleteAsync();
  foreach (var point in run.Result(best))           // point.Evaluations, point.Elapsed, point.Value
      Console.WriteLine($"{point.Evaluations}: {point.Value}");
  ```

  - No new layer or type kind: a ready-made analyzer is an ordinary analyzer (D64), so a substitution bundle. A caller either applies it to get a new configuration (`Substitute`, `AnalyzedBy`) or passes it to `CreateRun`, which applies it first. `CreateRun` takes any bundle, so counters, traces and plain substitutions attach there too.
  - Analysis is opt-in. Without analyzers the execution graph carries no wrapper and no cost; nothing is recorded by default at the level of the run, the scope or the trace machinery.
  - Defaults belong to the particular ready-made analyzers, not to the execution system: which evaluators a best-so-far analyzer observes when none is named, and the time axes its points carry (the candidates its evaluators evaluated, and the run's elapsed time). A general trace still records no clock it was not given.
  - The source, wrapper, counter and clock layer stays underneath for custom axes, nested algorithms and external roles.

- **D68. A ready-made analyzer observes the innermost evaluators by default.** When no evaluator is named, its substitution selects every evaluator that holds no other evaluator among its declared children. The predicate walks only the node's own children, so it is an ordinary substitution; the outermost evaluator of each slot cannot be selected that way, because a predicate does not see what holds a node. With `Cached(E)` the analyzer observes `E`, so its evaluation axis counts candidates actually evaluated; with `Counted(E)` it observes `E` once. A composite evaluator that combines child evaluators, or an evaluator inside a refiner that scores an inner problem, is observed at the wrong level; naming the evaluator, wrapped or not, overrides the default.
- **D69. The candidate type comes from a type argument, or from the named evaluator.** `Analyzer.BestSoFar<RealVector>()` when none is named, and `Analyzer.BestSoFar(evaluator)`, which infers it. Binding the type inside `CreateRun` was rejected, because it would need a new interface for bundles placed generically.
- **D70. Best so far is the first ready-made analyzer.** Others, such as population quality per iteration or a Pareto front, follow only once the design has proven its value.
- **D71. `CreateRun` takes analyzers as a collection.** Both algorithm `CreateRun` overloads get an optional `IReadOnlyList<ISubstitutionBundle>? analyzers` before `validate`, written with a collection expression: `ga.CreateRun(problem, random, [best])`. The developer prefers the explicit brackets to a `params` overload. Only the six forwarding calls of `Stream`, `Complete` and `CompleteAsync` in `AlgorithmExtensions.cs` pass `validate` positionally; they change to `validate: validate`. `Stream`, `Complete` and `CompleteAsync` keep their parameters.
- **D72. `Analyzer.BestSoFar` and `Analyzer.BestCandidateSoFar` replace the source-level `TraceBestSoFar` and `TraceBestCandidateSoFar`.** Their capability survives as optional arguments: `clocks` for further axes, read with `point.At(clock)`, and `retention`, still recording improvements only by default. Each has an overload without an evaluator (D69) and one naming it.
- **D73. Experiments take analyzers later, and phase 6 builds what they can use.** Phase 6 changes only algorithm runs; `ga.AnalyzedBy(best).Repeat(2)` keeps working. Constraints for the later experiment form: one analyzer serves every trial and each trial's run owns its result, as today; a ready-made analyzer only substitutes inner evaluators and never wraps the receiver, so substituting into a trial's algorithm keeps its concrete type; points with fixed evaluation and elapsed axes are comparable across trials, which aggregating curves over repetitions needs. Experiments are not configuration nodes, and grids key trials by their configuration (`GridExperiment.cs`), so substituting analyzers into each trial would change its key. Phase 7's explicit trial identity comes first.
- **D74. Phase 6 has two steps, each with its own spec, delegated implementation, review and commit.** Step 1, the foundation: analyzers as configuration nodes with one result table (D64), reading clocks (D65), the one-line form and the renamed observation interface (D66), and idea 10's fixed trace rows. Step 2, simple analysis: `CreateRun` with analyzers (D71) and the best-so-far analyzers (D67 to D70, D72). Later decisions add D86 to D89 to step 1 and D90 and D91 to step 2. D92 and D93 follow up step 1 after its review, and D94 to D102 belong to step 2. D103 adds step 3 on 2026-11-18, with its own spec, review and commit, and D106 to D111 refine it the same day.
- **D75. `Aggregate` is the provisional name of the one-line form, and "instrument" leaves the library in step 1.** `source.Aggregate(create, update)` follows LINQ's fold. That the glossary lists _Aggregation_ as legacy does not matter, because phase 8 removes every legacy term. The developer wants _instrument_ gone as soon as possible: step 1 removes it from every public type, member, parameter and file name, test name and documentation page (50 files mention it today: 25 in `src`, 17 in `test` and 8 in `docs`), including `IObservationInstrument<T>`, the `Instrument` property and parameter of `Observed` and `ObservedAlgorithm`, `InstrumentSpecs` and `InstrumentPlacementTests`. The replacing name is open.
- **D76. Analysis has four components, and the receiving end is the analyzer.** (1) The wrapper hooked into execution, which sees each call first hand and builds a record of it; (2) the observation, plain data; (3) the analyzer, the handle a user keeps, which places the wrappers, creates each run's result and takes the records, including a callback that keeps no result; (4) the result, whatever domain object the analyzer gives the user to read. The separate receiving-end concept (`IObservationInstrument<T>`) is fused into the analyzer; an interface remains only because one analyzer can take records of several types, and it is named and documented as part of the analyzer. The boundary (`.Invocations`, `.Iterations`, `.Calls`) stays as an expert concept, because its syntax is unusual; ready-made analyzers find their boundaries themselves (D68). Placing and reading stay one call each, and counting, timing, clocks and trace internals are author and expert concerns. Names of the first three components are open.
- **D77. The components keep their names: `Observed`, observation and analyzer.** The wrapper stays `Observed` (concept: observer), beside `Counted`, `Timed` and `Retry`; the record stays an observation, such as `MutationObservation<T>`; the fused component is the analyzer, with `Analyzer<TResult>` as its base and `IObservationAnalyzer<T>` as what it implements for each observation type it takes, replacing `IObservationInstrument<T>`. The wrappers' property becomes `Analyzer`, so `mutator.Observed(best)` reads as observed by the best-so-far analyzer. Considered and not chosen: tap, probe and hook for the wrapper; event and call for the record; tracker and recorder for the analyzer. With this, the names in step 1 are settled.

#### Phase 6 questions after the review on 2026-11-16

Step 1:

- **D78. The callback behind `Observing` is not an `Analyzer<TResult>`.** D76 counts it as an analyzer and D77 names `Analyzer<TResult>` as the base, but the callback lives in `Inspection` so that content such as racing can use it (D51), the base lives in `Analysis`, and `Action<T>` is not an `IRunResult`. An analyzer's result always spans the run; a `Share` does not narrow it.** This withdraws draft item 1's sentence that a `Share` narrows it as it narrows a counter's. `CreateRecorder(RunResults)` and `CreateReader(RunResults)` see no scope, and `run.Result` and `ResolutionScope.RunResult` always read the root, so a narrowed result could be written but never read. A Cycle's turns need the one run-wide result (D64), and a caller who wants one result per inner algorithm places one analyzer on each. What a `Share` leaves alone is the result that recorders write and `run.Result` reads. Resolving the analyzer directly through a scope that shares it still creates a separate execution node, which nothing records into; nothing guards against sharing an analyzer, and the wording elsewhere says so (amended on 2026-11-18).

- **D81. Observing adaptation values is deferred to the backlog.** Phase 5 left it to phase 6, and no scenario needs it yet.

Follows from D65 without a decision: an external type cannot implement an internal interface member, so `IClock<TTime>` implements the internal untyped read by default through `CreateReader`, and an external clock writes only `CreateReader`. Step 1 tests one.

#### Phase 6 simplifications after the second review on 2026-11-17

- **D86. `Aggregate` wraps its state in a library result.** A one-line analyzer should not need a result class of its own, which D79 required because a result implements `IRunResult` (D64). The library's `Aggregate<TState> : IRunResult` (name provisional) holds the state as `Value`, so `mutator.Invocations.Aggregate(() => new Dictionary<int, int>(), (sizes, observation) => …)` works and is read with `run.Result(sizes).Value`. This amends D79: the analyzer is `AggregateAnalyzer<TObservation, TState> : Analyzer<Aggregate<TState>>`, and the state type needs no marker. Updates of one run's state stay serialized, because observations from parallel execution can arrive together, as for traces.
- **D87. The rank analyzer composes the genealogy analyzer.** Rank places its own iteration hook and then the genealogy's substitutions, so the genealogy's wrapper sits closer to the algorithm and closes a generation before rank reads its ranks, as a trace places its clocks (D28). Rank's result holds the genealogy's graph, read from the run's results. Rank holds a genealogy analyzer and derives from nothing but `Analyzer<RankState<TCandidate>>`, so this is composition. The forwarding observation interfaces, `GenealogyAnalyzer.Recording` and the empty abstract `RankAnalyzer<TCandidate>` go; PythonInterop names `Analyzer<RankState<TCandidate>>`. It is a test case for one analyzer built on another through public API.
- **D88. A trace's result is `Trace<TValue>`.** `run.Result(trace)` no longer names the observation type. `Trace<TObservation, TValue>` becomes an internal subclass that keeps the run's value function, and the recorder casts to it. Whether every trace is enumerable directly is decided with D85 in step 2.
- **D89. `InvocationSource` builds its `Observed` wrapper itself.** It gets the observation constraint that `AlgorithmSource` has, so it constructs the wrapper directly and drops its delegate field.

Step 2:

- **D90. One best-so-far analyzer.** `Analyzer.BestSoFar` records improvements whose points give the objective vector as `Value` and the candidate as `Candidate`, besides the time axes. `BestCandidateSoFar` is not added, which amends D72 and removes its value-or-candidate axis. Each retained point keeps a reference to its candidate; with improvements only by default, that stays small.
- **D91. `AnalyzedBy` is removed.** A caller who wants the configuration with its analyzers placed calls `Substitute`; otherwise `CreateRun` places them (D71). This amends D59, which kept `AnalyzedBy` as a name for `Substitute` typed by the receiver's interface: an analyzer that wraps the receiver itself, such as a trace of its iterations, now needs a receiver typed by the interface. D73's example becomes `ga.Substitute(best).Repeat(2)`, which keeps the concrete type because a ready-made analyzer never wraps the receiver. D57's error message and the guide lead with `CreateRun(problem, random, [analyzer])`. Both `AnalyzedBy` extensions and `AnalysisPlacement` go, with their 197 uses migrated.

#### Phase 6 decisions after the design pass on 2026-11-17

A read-only design pass over step 1's code and over substitution and placement before step 2 raised these questions. The developer decided them on 2026-11-17, during the review of step 1.

Step 1 follow-ups, applied after the developer's review of step 1:

- **D92. The untyped clock read is public.** `IClock.CreateUntypedReader(RunResults)` becomes public, and `IClock<TTime>` keeps implementing it by default through `CreateReader`, so an external clock still writes only `CreateReader`. An external analyzer can then read a mixed clock list such as `[evaluations, Clock.Elapsed]` as a trace does; while the read is internal, only built-in analyzers can. This amends D65's "internal". Superseded by [D103](#phase-6-decisions-on-2026-11-18) on 2026-11-18: the public boxed read is the reading's `IClockReading.Read()`.
- **D93. Step 1's analyzers check their arguments alike.** The Pareto front and best-before-change analyzers keep each evaluator once by reference and throw `InvalidOperationException`, as traces and `Aggregate` do, where they now record a repeated evaluator twice and throw `ArgumentException`. Rank's `algorithms` becomes its required first constructor parameter, since an empty list is already rejected. Traces report a clock they do not use with one message instead of two. The callback behind `Observing` is not changed here, because D100 gives it a new base.

Step 2:

- **D94. `CreateRun` places the analyzers, validates, builds the run and then checks that it holds them.** It makes one `Substitute` call with the analyzers it was given, so a clock shared within the list updates once and before the traces that read it (D28). Validation then checks the graph that runs. After building the run, it runs D57's held check for each given configuration whose result a run reads, such as an analyzer, counter or duration, so a default selection that matched nothing, for example because of the wrong candidate type, fails at once instead of after a run that recorded nothing. Amended on 2026-11-18 to the order the code implements. A receiver typed by its interface is what `AnalyzedBy` added, and `CreateRun` places into the algorithm it receives, which removes the last reason for `AnalyzedBy` (D91). Amended by [D103](#phase-6-decisions-on-2026-11-18) on 2026-11-18: counters and durations are no longer passed to `CreateRun`, their placing substitutions are, so the check concerns analyzers and clocks that place themselves ([D110](#phase-6-step-3-decisions-on-2026-11-18)).
- **D95. `CreateRun` places analyzers after budgets.** A budget holds a copy of its algorithm (`OperatorCountBudgetAlgorithm.cs:122`), so a trace on `ga.Iterations` passed to the run of `ga.LimitedToInvocations(…)` finds nothing. This reverses D58's "analyze first, then budget" for the `CreateRun` path. Step 2 documents the order, and D17's message says how to name the target from the budgeted configuration. Ready-made analyzers with the default selection are not affected, because they do not name `ga`. [The backlog item](developer-backlog.md#runs-execution-and-experiments) on one rewrite that also takes budgets is revisited after step 2.
- **D96. The default selection skips an evaluator that holds another anywhere below it.** This sharpens D83: a ready-made analyzer selects the evaluators of its candidate type that hold no such evaluator anywhere among their declared descendants, not only among their direct children. Then no observed evaluator sits inside another observed one, so no evaluation is counted twice. For the built-in algorithms both readings select the same evaluators. Evaluators inside refiners are observed too; their evaluations are real, and the guide says so.
- **D97. The best-so-far analyzer counts through a counter it places.** It reuses the existing mechanisms instead of counting by itself: its group lists its observer placements and then a counter of the candidates its selected evaluators evaluate, so under D28 the counter sits closer to each evaluator and a point includes its own call. The analyzer reads that counter as a clock. By default the evaluation count is its only axis. Time is a clock the caller passes in `clocks`, such as `Clock.Elapsed`, and is read with `point.At(clock)`. Points give `Evaluations`, `Value`, `Candidate` and `At(clock)`. This amends D67, which named the run's elapsed time as a default axis, D85, which listed `Elapsed` among the points' members, and D90's "time axes". An analyzer that adds up `observation.Candidates.Count` itself was considered and rejected; [the backlog](developer-backlog.md#a-best-so-far-analyzer-that-counts-by-itself) records why.
- **D98. Every trace is enumerable.** `Trace<TValue>` enumerates a snapshot of its entries, so a trace reads like the best-so-far result (D85); `Snapshot()` stays. This settles the question D88 left to step 2.
- **D99. PythonInterop moves to the best-so-far analyzer.** Its best-so-far trace (`QualityCurve`) is placed but never read by `ToExperimentResult`, also on `main`. It is not simply removed: PythonInterop uses `Analyzer.BestSoFar`, its points go into the Python `ExperimentResult`, and a Python sample plots the curve. Only then do the old form and `TraceBestCandidateSoFar` go. `ExperimentResult<T>` is a record that holds `IReadOnlyList` fields; it holds `ValueArray` once touched.
- **D100. `ISubstitution`, `Substitution` and `SubstitutionGroup` replace `ISubstitutionBundle`.** The bundle's working name is retired, as the backlog asked at this point.
  - `public interface ISubstitution` has one member, `IReadOnlyList<Substitution> Expand()`: the single substitutions it stands for, in the order a call applies them, the same instances on every call. `Substitute(params IReadOnlyList<ISubstitution>)` and `CreateRun(…, IReadOnlyList<ISubstitution>? analyzers)` take it.
  - `Substitution` stays one sealed class for a single rewrite: a node type, a selection, a replacement and an optional target. Its `Of` factories are the only way to create one, and its `Expand()` returns itself. Predefined substitutions are factory methods grouped by concern, as `Counting` and `RecordingInto` are, or named types deriving from `SubstitutionGroup`. Users do not define new kinds of single substitution, because substitutions are not named concepts that are stored (D101). A derivable `Substitution<TNode>` with abstract `Selects` and `Replace` was considered and deferred; [the backlog](developer-backlog.md#scenarios-awaiting-a-concrete-need) records its trigger.
  - `public abstract class SubstitutionGroup : ISubstitution` represents substitutions that belong together. It implements the interface directly and does not derive from `Substitution`. Authors list its parts in `protected abstract IReadOnlyList<ISubstitution> CreateSubstitutions()`, and a part may itself be a group; `Expand()` returns the expansion of its parts, built once and cached. Only the group holds parts. Its documentation says that the order of parts matters, a later part sitting closer to its target, and that a shared part such as a clock is listed after what reads it. `Analyzer<TResult>`, `Counter`, `Duration` and the callback behind `Observing` derive from it; a trace lists its clocks directly, and rank lists the genealogy analyzer. Superseded in part by [D103](#phase-6-decisions-on-2026-11-18) on 2026-11-18: `Counter` and `Duration` no longer derive from it, and a trace lists no clocks.
  - Applying stays in the call, because it needs the whole expanded list: a substitution listed twice applies once at its last position, every target is matched against the graph the call received, and D57's check reads it. Expansion is depth-first and in place, so a group's substitutions take the group's position, exactly as a trace spreads its clocks' substitutions today. A group that contains itself is an error. D57's check uses the expansion only to know whether a configuration expects placement; it still looks for the configuration itself in the graph.
  - The names describe what the types are: `CompositeSubstitution` was rejected as a pattern name, and `ExpandingSubstitution`, `Placement`, `SubstitutionSet`, `SubstitutionSequence`, `Instrumentation`, `SubstitutionModule` and `SubstitutionBundle` were considered.
  - This reverses D59's and the backlog's deferral of composites on 2026-11-10. Nesting still means nothing beyond order, but it removes the manual spreading from authors. The deferred `IAnalyzer` stays in the backlog. The glossary's _Substitution bundle_ becomes _Substitution_ and _Substitution group_, both provisional until step 2 is finished.
- **D101. Substitutions are never persisted.** A substitution is a rewrite applied while building a configuration. It is never stored or serialized. What you persist is the configuration it produced, which contains the nodes it placed. That configuration is an ordinary one, equal to the graph written by hand (D1), so persistence needs no knowledge of substitutions, and a substitution by reference could not match a loaded graph anyway. This replaces the route of reapplying substitutions after loading in [what does not simply disappear](#what-does-not-simply-disappear). Consequences, which the developer accepts:
  - What a substitution places must be data for the configuration to be persistable (§ 4.8). Analyzers that hold delegates, such as `Aggregate`, traces with value functions and `Observing`, make it non-persistable, as today.
  - Analysis has a persisted route and a run-time route. `ga.Substitute(best)` gives a configuration with the analysis in it, to persist as part of an experiment. `ga.CreateRun(problem, random, [best])` places the analysis only for the run, so it never becomes part of what the caller serializes. The second route is the run-time-only list the backlog's item on delegates in analysis definitions asked for.
  - A substitution cannot be undone. A caller who also wants the configuration without instrumentation persists it before substituting.

  Still open, as before: the identity of shared nodes in a persisted graph, and how a loaded analyzer is found again so that `run.Result(analyzer)` works after loading.

- **D102. The best-so-far analyzer's counter is public.** Decided by the developer on 2026-11-17 after a correctness review found that `evaluator.Observed(best)` records points whose `Evaluations` stay 0: only `CreateRun` and `Substitute` could place the private counter of D97, which gave the built-in placement path a capability an explicit placement lacked. `BestSoFarAnalyzer<TCandidate>.Evaluations` exposes the `Counter`, so the explicit form is `evaluator.Counted(best.Evaluations, OperatorCountMetric.Candidates).Observed(best)`, and a terminator may read the same count. This amends D97's private counter.

#### Phase 6 decisions on 2026-11-18

Decided by the developer on 2026-11-18, so that configuration graphs can be serialized. The rule behind them: a configuration node is serializable data, while an execution node may hold anything, including a time provider, a problem or a delegate. The [step 3 decisions](#phase-6-step-3-decisions-on-2026-11-18) D106 to D111 answer the questions of the spec's first draft; D103 is stated here as they refine it.

- **D103. Clocks are configuration nodes, counters and durations place nothing, and time comes from the run.** Four parts of the configuration graph hold more than data today: `IClock` is a mechanism of its own whose readers are delegates (`CreateReader`, `CreateUntypedReader` and the traces' `Func<object>[]`); a counter or duration created from a source holds a placement delegate (D25); `Duration`, `AfterElapsedTimeTerminator` and `AlgorithmDurationBudgetAlgorithm` hold a live `TimeProvider` (D53); and `EpochClock` holds a live problem. The first three move to the execution side; the epoch clock keeps its problem as a documented exception (D107).
  1. **A clock is a configuration node whose execution node is its reading for the run.** The reading is a run result, so the run's root owns it and `results.Result(clock)` returns it. `IClockReading : IRunResult` has `object Read()`, and `IClockReading<out TTime> : IClockReading` has `new TTime Read()` and implements the boxed read by default, so a reading writes only its typed read. There is no clock interface (D106): a typed read takes `IConfigurationNode<IClockReading<TTime>>` and infers `TTime`, and a mixed clock list is typed `IReadOnlyList<IConfigurationNode<IClockReading>>`, which the covariance of `IConfigurationNode<out TExecutionNode>` fills from `[evaluations.Clock, Clock.Elapsed]`. The non-generic reading is the smallest shape for the boxed read: variance does not convert `IClockReading<long>` to `IClockReading<object>`, because `long` is a value type, so clocks of `long` and `TimeSpan` share no generic reading, while every reading converts to `IClockReading` by reference. It follows `IEnumerator` and `IEnumerator<T>`, one name for one operation. A counter or duration is not a clock; `counter.Clock` and `duration.Clock` are (D106). `Clock.Elapsed` returns the public record `ElapsedClock` (D111), and the epoch clock is a configuration node whose reading reads its problem (D107). `IClock`, `IClock<TTime>`, `CreateReader`, `CreateUntypedReader` and the reader delegates go.
  2. **Counters and durations are leaves that place nothing.** `Counter` and `Duration` hold no placement and are no substitution groups. A source returns the substitution that places a wrapper for a counter or duration the caller supplies: `Counting(counter)`, `CountingCandidates(counter)` and `Timing(duration)` (D109). Clocks only read, and placement is explicit and separate (D110): no trace and no best-so-far analyzer places any clock; the caller passes a counter's or duration's placement, or a clock that places itself, to `CreateRun` or `Substitute`, listed after the analyzers that read it, so that its wrapper sits closer to the target and a reading includes the call (D28, D36). `Analyzer.BestSoFar` keeps placing its own `Evaluations` counter (D97, D102), which is its count, not one of its clocks. This returns to D31's rule that a source installs nothing. Accepted consequences: a counter read from a run that never placed it reads zero instead of failing, while a placement whose target the graph does not hold fails at once (D17); and a clock shared by traces placed in separate `Substitute` calls ticks once, because only its own placement places it, which closes D36's known gap.
  3. **Clocks match by equality.** Trace columns and their deduplication, `TraceEntry.At`, `TraceSnapshot.By`, `BestSoFarPoint.At` and the best-so-far analyzer's clock list compare clocks with `Equals` instead of `ReferenceEquals`. `Counter` and `Duration` stay classes without `Equals` overrides, so they match by reference: two counters are different counters, and copies of a configuration keep the same counter (D39). `CounterClock` and `DurationClock` are records over their node, so two clocks of one counter are equal and clocks of two counters are not. `ElapsedClock` holds no data, so all elapsed clocks are equal, also after a persisted graph is loaded. The epoch clock holds a live problem and stays a class (§ 4.9), so it matches by reference (D107). Resolution keeps keying execution nodes by reference, so two equal clock instances in one run get two readings, which read the same values.
  4. **The run holds the time provider.** No configuration node holds a `TimeProvider`. The run's `RunResults`, created by `ResolutionScope.Create(TimeProvider)` and already measuring `Elapsed`, holds it behind a public getter (D108), and execution nodes read `scope.Results.TimeProvider` when they are built: the `Timed` and `TimedAlgorithm` wrappers, the executors of `AfterElapsedTimeTerminator` and `AlgorithmDurationBudgetAlgorithm`, and wrappers of a user's own such as the guide's `SlowCallReporter`. The elapsed reading reads `RunResults.Elapsed`, which uses it already. The accumulators need none, because the wrappers that add time hold it. Tests inject a fake provider through the internal `ResolutionScope.Create(TimeProvider)` and the internal `AlgorithmRun` constructor (D63); nothing public chooses the provider. Every public `timeProvider` argument and `TimeProvider` member of a configuration goes; an executor may still take a `TimeProvider` in its constructor.
  5. **The epoch clock reads the problem it was given** (D107). `EpochClock<TCandidate, TSearchSpace>` keeps its `IDynamicProblem<TCandidate, TSearchSpace>` and becomes a configuration node whose reading reads `Problem.CurrentEpoch`. A configuration holding it is not serializable, which its documentation and the § 4.8 exceptions of the developer guidelines state. The run gets no problem and no other public state for it.

  This supersedes D25 in part (counters and durations from sources that place themselves, a trace attaching its clocks), D43 (`Substitution.Counting` as the one-call form), D52 in part (`Count()`, `CountCandidates()` and `Duration()` on sources), D53 in part (the `TimeProvider` on the node), D59 and D100 in part (counters and durations as substitutions, a trace listing its clocks), D65 (clocks read through `CreateReader`, traces placing clocks) and D92 (the public `CreateUntypedReader`). It amends D11 and D60 (the placement lambda, and `LimitedToDuration` without `timeProvider`), D36 (the caller lists a clock's placement), D57 (the check concerns configurations that place themselves, analyzers and clocks that observe) and D94 (counters are not passed to `CreateRun`; their placements are). D28, D39, D63, D97 and D102 stay. It also takes up what the backlog rejected as ["counters only from `Counting(..., out)`, with passive clock definitions for traces"](developer-backlog.md#analyzer-placement-alternatives-rejected-on-2026-11-08): that entry's cost was a second way to count beside self-placing counters, and with D103 there is one way.

- **D104. `RankAnalyzer.Genealogy` is public.** An analysis node in the configuration graph must be public, so that a caller can place it by hand. Since D87, `algorithm.Observed(rank)` recorded no generations, because the genealogy analyzer that builds rank's graph was private and only rank's own substitutions placed it; the automatic path had a capability the explicit one lacked, as D102 found for the best-so-far counter. `RankAnalyzer<TCandidate, TSearchState>.Genealogy` exposes it, and its remarks say that an explicit placement places it too. Already applied in `RankAnalyzer.cs`. This closes the open item of the second correctness review in step 2's implementation note; item 4 of step 3 adds its test.

An interface shares a file with its one primary implementation.** The file is named after the implementation, and an interface with a single implementation that will likely stay single is questioned for necessity. Published interfaces are not removed for this, because the library ships as a package. Recorded as § 9.9 of the [developer guidelines](../docs/contributing/developer-guidelines.md); the uncommitted tree already applies it to the RoarNet interfaces, `IRegressionModel` and `IQuadraticAssignmentProblemData`.

#### Phase 6 step 3 decisions on 2026-11-18

The developer answered the six open questions of step 3's first draft on 2026-11-18. Q1 and Q5 were answered with designs of the developer's own; Q2 chose option B; Q3, Q4 and Q6 settled what the draft asked. D103 above is worded with them.

- **D106. A clock is not a counter.** (Q1) The draft made counters and durations clocks through their accumulators. Then `Counter` would implement `IConfigurationNode<CountAccumulator>` and a second construction for its reading, which breaks the inference of `run.Result(counter)` (CS0411) and about 330 reads of `CurrentCount` and `CurrentDuration`. The developer separated the two concepts instead.
  - `Counter : IConfigurationNode<CountAccumulator>` and `Duration : IConfigurationNode<DurationAccumulator>` stay single-purpose leaves: no clock interface, no placement field or delegate, no `TimeProvider` and no `SubstitutionGroup` base, which nothing needs on them once they place nothing (D103 item 2). `run.Result(counter)` and every `CurrentCount` and `CurrentDuration` read stay unchanged and keep their inference. `CountAccumulator` and `DurationAccumulator` implement no clock reading.
  - A clock is any configuration node whose execution node implements `IClockReading<TTime>`. There is no `IClock` interface. Typed signatures take `IConfigurationNode<IClockReading<TTime>>`, and mixed lists `IConfigurationNode<IClockReading>`. The non-generic `IClockReading` with its boxed `object Read()` stays, because a trace's row of mixed clocks needs it (D103 item 1).
  - A counter is watched by a separate clock. `counter.Clock` returns `public sealed record CounterClock(Counter Counter) : IConfigurationNode<IClockReading<long>>`, whose reading reads the root's accumulator through `scope.Results.Result(counter)`, with the guarantees of today's reader: the root's count whatever a `Share` narrows, thread-safe, and created once per run and clock instance. `duration.Clock` returns `DurationClock` likewise. Each declares its node as a parameter, as `Counted` and `Timed` do, and holds no collection. Two clocks of one counter are equal by value, because the counter compares by reference.
  - `Clock` is a computed property that returns a new record on every read. Value equality makes caching unnecessary: traces deduplicate and find columns with `Equals`, and a second instance resolved in one run costs only a second reading of the same accumulator. A cached instance would also make every counter hold its clock, which holds the counter.
  - Where a counter or duration is a trace clock today, as in `Trace(…, [counter])`, `At(counter)` or `By(counter)`, it becomes `counter.Clock`. Passing the counter itself no longer compiles, because `CountAccumulator` is no reading; the compiler reports CS0411 for `At(counter)` and a conversion error for a clock list.

  Checked against the code on 2026-11-18. `IConfigurationNode<out TExecutionNode>` requires `class, IExecutionNode`, which both reading interfaces meet as interfaces deriving from `IRunResult`. `CounterClock` converts to `IConfigurationNode<IClockReading>` by covariance, because `IClockReading<long>` converts to `IClockReading` by reference. `At(counter.Clock)` infers `TTime` as `long` through both covariant parameters, and a clock whose node type is its own reading class, such as `IConfigurationNode<CallCount>` with `CallCount : IClockReading<long>`, infers the same way. `ResolutionScope` gives every `IConfigurationNode<IRunResult>` to the root (`ResolutionScope.cs:146`), which covers every clock by the same covariance. CS0411 remains possible only for a type implementing two `IConfigurationNode` constructions or a reading implementing two `IClockReading<T>` constructions; after D106 no library type does.

- **D107. The epoch clock keeps its live problem as a documented exception.** (Q2, option B) `EpochClock<TCandidate, TSearchSpace>` stays a sealed class holding `Problem`. It implements `IConfigurationNode<IClockReading<int>>`, and its private reading reads `Problem.CurrentEpoch`, so it is a clock in D106's sense. It holds a live object, so it is a class (§ 4.9) and matches by reference; callers keep the instance they gave the trace, as they do today. `Clock.FromEpoch(problem)` keeps its argument. It declares no parameters, because its problem is no configuration child. Its documentation and the list of § 4.8 exceptions in the developer guidelines say that a configuration holding it is not serializable. `RunResults` gets no `Problem`, and the run no other public state for the epoch clock; the draft's option A is not taken. Option C, an epoch clock that observes evaluations and reads `observation.Problem`, is a [future consideration in the backlog](developer-backlog.md#scenarios-awaiting-a-concrete-need).
- **D108. `RunResults.TimeProvider` is public.** (Q3) A built-in timing wrapper may do nothing that an external wrapper cannot do the same way, so the getter is public from item 1 on. The guide's `SlowCallReporter` (`test/HeuristicLib.Tests.Docs/Extending/CustomWrapperDocumentationSpecs.cs`) and the wrapper guide read `scope.Results.TimeProvider` instead of holding a provider. Choosing the provider stays internal: `ResolutionScope.Create(TimeProvider)` and the internal `AlgorithmRun` constructor, which only the core test suite sees. What the public getter changes: an external or Experimental timing node can measure with the run's provider, which removes the draft's risk that Experimental could not, and the guide's example no longer holds a provider. What it does not change: the API usage, documentation and Experimental suites still cannot inject a provider, so their timed tests still move to budgets whose outcome does not depend on time, and exact timed assertions still move to the core suite.
- **D109. The counting and timing forms.** (Q4, accepted as recommended) The wrappers `Counted`, `Timed`, `CountedAlgorithm` and `TimedAlgorithm`, the source substitutions `Counting(counter)`, `CountingCandidates(counter)` and `Timing(duration)`, and the root forms that create their node with `out` stay. The root forms over an existing node, `Counting(target, counter)` and `Timing(target, duration)`, and every `Substitution.Counting` and `Substitution.Timing` overload go, as duplicates of `root.Substitute(source.Counting(counter))`. The root `out` form keeps its `OperatorCountMetric` parameter, because generic code over the operation, such as the budgets, cannot reach `Invocations`, while a source names the metric (`CountingCandidates`).
- **D110. Clocks only read; placement is explicit and separate.** (Q5, reworked) A clock that needs a wrapper placed is not an analyzer: offering substitutions does not make a node an analyzer. Such a clock also implements `ISubstitution`, usually by deriving from `SubstitutionGroup`, and the caller passes it to `CreateRun` or `Substitute` in the list. A trace never places any clock, whatever the clock offers, and neither does the best-so-far analyzer. Counter and duration clocks need no placement of their own, because the `Counting` or `Timing` substitution places the node they read. In one list a later part sits closer to its target (D28), so a clock or a counter's placement is listed after every analyzer that reads it, and the reading then includes the call (D36); listed before them, it reads before the call. A clock that observes calls is a `SubstitutionGroup` that places an `Observed` wrapper for itself and implements `IConfigurationNode<TReading>` for its own reading and the observation interface `IObservationAnalyzer<T>` that `Observed` calls. D57's check covers it in a `CreateRun` list as it covers an analyzer, because it is a configuration node with a non-empty expansion that its `Observed` wrapper holds. The test clocks that derive from `Analyzer<CountAccumulator>` today take this shape in item 3 of step 3.
- **D111. The elapsed clock is the public record `ElapsedClock`.** (Q6) A persisted graph must name the elapsed clock's type, as it names `Counter`, `Duration` and `EpochClock`, so `public sealed record ElapsedClock : IConfigurationNode<IClockReading<TimeSpan>>` is public and has no parameters. `Clock.Elapsed` stays as a convenience returning an instance; all instances are equal.

### Phase 7: experiments on the parameter system

Grids can vary parameters through metadata in-process, and trials get explicit identity instead of using the configuration as their key (`GridExperiment.cs:28`, idea 11). Typed `VaryBy` stays. That identity comes before experiments accept analyzers, so that placing analysis cannot change a trial's key ([D73](#phase-6-decisions)); one analyzer definition then serves every trial, and each trial's run owns its result. #### Phase 7 decisions on 2026-11-18

A first proposal kept the experiment types and added ordinal keys, an untyped parameter write and analyzers on experiment runs; its review found that placing analysis only into each trial's run already keeps keys stable, and that the untyped write served construction from data rather than this phase. The developer then set the model: as in scikit-learn, a grid holds the variation, as `ParameterGrid` does, and an experiment orchestrates the runs over it, as `GridSearchCV` does. The experiment system may be reshaped to fit, and a Codex trial tries the new version out before the spec is written.

- **D116. A trial is identified by its position.** As in scikit-learn, a grid point is identified by its position in the grid's Cartesian order and a trial by its point and repetition. The configuration is no longer a key, so equal configurations at different points are separate trials; an accidental duplicate value runs silently and doubles that group's samples, which the guide states. The settings that label a point come from D118.
- **D117. A grid varies a parameter by its declared descriptor or by a typed lambda.** Both forms stay: one names the parameter and its values, the other takes the values and a typed configurator, which remains the form for coupled settings, such as elites derived from the population size. The descriptor form is typed, so a value of the wrong type does not compile. An untyped write through an `IParameter` known only at run time belongs to string-based configuration, which the developer expects to need soon; it is not part of this phase.
- **D118. A grid knows the parameters it varies.** It keeps its varied descriptors, so each trial can report its settings by name, as scikit-learn's `params` and `param_<name>` do; a dimension varied by a lambda carries no label. The descriptors also prepare string-based configuration.
- **D119. Experiments place analyzers after variation.** The experiment's `CreateRun` takes the same `substitutions` list as algorithm `CreateRun` and places it into each trial's run, after the grid has produced the trial's configuration. The trial's configuration stays as the grid produced it, the trial's run holds the graph that ran, and each trial's run owns its result, read with `trial.Run.Result(definition)`. A configuration with analysis already placed also works as long as the grid does not replace what the analysis observes. D73's constraint that a ready-made analyzer never wraps the receiver existed to keep configuration keys stable and no longer applies.
- **D120. `Grid<T>` is not enumerable.** The rule that a record never holds or declares an `IEnumerable` covers implemented interfaces. `Grid<T>` drops `IEnumerable<T>`, `IEnumerable` and its public `GetEnumerator`, and its configurations are read through one property.
- **D121. Results are read per trial.** There is no cross-trial results view such as scikit-learn's `cv_results_`; grouping and aggregation over trials use ordinary LINQ.
- **D122. Repetition _r_ of every grid point shares one random stream by default.** This gives common random numbers across settings, as scikit-learn scores every candidate on the same splits. Whether and how a caller can choose independent streams instead is open.

The first Codex trial stopped before changing code: with a grid generic in any `T`, `grid.Repeat(5)` cannot infer the algorithm's candidate and search-state types (CS0411), and the problem passed to `CreateRun` does not supply the search state either. It found that the only custom experiment is a test fixture, that one checked conversion keeps the concrete type for an inherited descriptor, and that a type predicate observes the root of every grid copy but also matches nested algorithms of that type.

- **D123. The grid is an algorithm grid that keeps its dimensions.** `Grid<TCandidate, TAlgorithm, TSearchState>` replaces the generic `Grid<T>`; `ga.AsGrid()` and `Grid.Create(ga)` infer its types from the algorithm, so `grid.Repeat(5)` compiles. A child, such as a selector, is varied by a list of values for its descriptor; there are no nested grids. The grid keeps its dimensions, each a descriptor or a typed lambda with its values, and decodes a point from its position, as scikit-learn's `ParameterGrid[i]` does, so that a later tuning algorithm can use the grid as its search space ([backlog](developer-backlog.md#scenarios-awaiting-a-concrete-need)).
- **D124. The experiment chooses how random streams fork.** One property on the experiment, set with `with`, chooses between the default of D122, where repetition _r_ of every point forks the same stream, and independent streams per trial. Every trial still gets its own generator.
- **D125. Experiment `CreateRun` validates like algorithm `CreateRun`.** It takes `validate = true` after `substitutions` and passes it on, so each point's configuration is checked, with its analysis placed, before the run is returned. A placement or validation failure names the point and repetition.
- **D126. Tuning is an ordinary algorithm, later.** Grid search, random search and other tuners over a grid are ordinary algorithms with a meta-problem, generalizing Experimental's `MetaOptimizationProblem` and racing; experiments stay as the separate system that runs every point and keeps each run. Recorded in the [backlog](developer-backlog.md#scenarios-awaiting-a-concrete-need), not part of this phase.
- **D127. Analyzers named on the prototype's root do not serve a grid.** An analyzer such as `ga.Iterations.TracePopulationQuality()` names the prototype, which no grid point holds, so its placement fails at run creation; it works with `ga.Repeat(n)`. The guide states this, and the [backlog](developer-backlog.md#algorithms-representations-and-analysis) keeps the question of a root-only selection.

- **D128. An experiment has one fixed shape: points × problems × repetitions.** `IExperiment`, its `TKey`, the abstract `Experiment` record, `GridExperiment`, both `RepeatedExperiment` forms and `ExperimentCase` go; nothing in the repository needs a custom experiment, and an extension point comes back when a concrete experiment kind needs one ([backlog](developer-backlog.md#scenarios-awaiting-a-concrete-need)). A trial is identified by its problem, its point and its repetition, each a position. Repetitions default to one, so `.Repeat(n)` is optional: repeating a single algorithm is `ga.Repeat(10)`, and a grid without `Repeat` runs each point once.
- **D129. Variation, repetitions and the stream setting live in one type.** This amends D123: the algorithm grid is the experiment. `ga.AsGrid()` builds it, and it carries both `VaryBy` forms, `Repeat`, the stream property of D124 and the run conveniences. A separate grid would need every run convenience forwarded to the experiment, because C# extension members ignore implicit conversions. Its points stay decodable by position for a later tuner (D126). The trial proposes the type's name.
- **D130. Problem instances are given when the run is created.** Beside the single-problem form, `CreateRun` takes a list of problems, such as `experiment.CreateRun([rastrigin10, rastrigin20], random, [best])`, so the experiment stays data and problem-bound executors bind as before (D5). Problems of different types that share the candidate and search-space type are passed through the interface `IProblem<TCandidate, TSearchSpace>`, as the existing interface overload does. The trial reports its problem. This amends D122 and D124: shared streams fork by problem and repetition and are shared across points, and independent streams fork by problem, point and repetition.
- **D131. Blocks are concatenated.** As scikit-learn accepts a list of grids, an experiment's points are a sequence of blocks, each a Cartesian grid or a list of configurations a script generated. `Concat` appends another experiment's blocks, and a list form makes a block of given configurations; there are no other combinators in this first draft. Points are numbered across the blocks, each point carries its own block's labels, and all blocks share one algorithm type, so mixing algorithm types needs blocks typed by the algorithm interface. Repetitions and the stream setting belong to the whole experiment.

### Later simplifications recorded on 2026-11-15

Raised in the review of the phase 4b change and deferred by the developer. None is accepted as a design unless its entry says so; each needs its own discussion before implementation.

- **Fewer executor base classes.** About 30 public executor bases remain, three per candidate role and more for termination, interception and algorithms. Since D5 each one only stores `problem` and `searchSpace`, and the candidate-only ones are empty. The developer wants authors to keep deriving from a base that fits them rather than implementing the executor interface, so the bases stay as a concept. The question is how many are needed, for example whether the search-space-only arity earns its place beside the problem-bound and the empty one. Settled on 2026-11-19 by D149 and D150 in [phase 7b](#phase-7b-a-smaller-operator-authoring-api).
- **Bind the objective like the problem.** `Select` and `Replace` still take the objective on every call, and every algorithm passes `problem.Objective`, which D18 fixes for the lifetime of the problem object. Selection and replacement executors could read it from the problem they are bound to at construction, as problem-specific operators read their problem. For the genetic algorithm, the evolution strategy, NSGA-II and the hill climber it is the only thing their executor reads from the problem. To settle first: context-free selectors are their own executor today and would need a bound one, and selecting under a derived objective, such as a scalarization, would need another route. Settled on 2026-11-19 by D151 to D155 in [phase 7b](#phase-7b-a-smaller-operator-authoring-api).
- **One block of resolution extensions per role.** Each role repeats `Resolve`, `ResolveOptional` and `TryResolve` for the untyped scope, the three-argument typed scope and the four-argument typed scope. The executor type no longer depends on the scope's types, so the two typed blocks differ only in the search state they pass to the signature check. Look at this after phase 5 removes `Resolve<TControl>`. The developer accepted a trial on 2026-11-16, before phase 6, and reviews the result before deciding to keep it. Spec:
  - Every caller keeps every combination: each scope kind resolves each role with the same call as today. Only declarations shrink, and `ISearchSpace` does not replace `TSearchSpace` anywhere.
  - `ResolutionScope<TCandidate, TSearchSpace, TProblem>` gets two internal virtual methods, generic in the operation, that resolve and try to resolve an operator for this scope's problem with `ISearchState` as the search state. `ResolutionScope<…, TSearchState>` overrides both to pass its `TSearchState`. The three-argument classic `ResolveOperator` and `TryResolveOperator` extensions call them, so they check the run's search state when the receiver is a four-argument scope. The four-argument classic overloads stay public.
  - For the seven roles whose executor type does not name the search state (creation, crossover, evaluation, mutation, refinement, replacement, selection), the block on the four-argument scope goes; the three-argument block serves both scopes through the base class. Termination and interception keep their four-argument block, because their executor names the search state. Algorithm resolution is out of scope.
  - One behavior changes on purpose: a four-argument scope held as a three-argument one now checks its own search state instead of `ISearchState`. A test pins it, and one more resolves each of the seven roles through a four-argument scope.
  - Every in-repository caller compiles unchanged; documentation that lists the blocks follows.

  Implemented on 2026-11-16: added internal virtual resolution and try-resolution for the typed scope's problem, with four-argument overrides preserving the run's search state, and removed the seven duplicate four-argument role blocks. Added tests for all seven roles' resolution forms and the search-state check through a three-argument reference, and updated the operator authoring documentation. No deviation from the accepted trial spec.

- **Documentation to add in the phase 8 pass.** A new problem object per turn gets a new, empty executor, and the scope keeps the old one, so the meta-algorithm guide should say to update a subproblem in place or to use a child scope per turn. The wrapper guide should show the agnostic pattern for a wrapper that needs only an interface of the problem, as `DynamicCachingEvaluator` uses it. From [phase 7b](#phase-7b-a-smaller-operator-authoring-api): the operator guide shows how an operator that needs another objective is resolved under a small delegating problem created once per `CreateExecutor` (D152), and the algorithm guide shows that an objective varying during a run, such as MOEA/D's scalarization, is a value strategy of the algorithm.

### Phase 7b: a smaller operator-authoring API

Settles the first two items under [Later simplifications recorded on 2026-11-15](#later-simplifications-recorded-on-2026-11-15), discussed with the developer on 2026-11-19 before phase 8, because both change the operator-authoring API that phase 8 documents. Both are architectural and accepted.

Findings that shaped the decisions:

- Since D5 an executor base receives nothing from the library: it stores only what its author passes to its constructor. The executor ladder adds two protected properties, `Problem` and `SearchSpace`, and changes no check, signature or resolution. The configuration ladder is different: its arity controls `Supports`, the typed `CreateExecutor` scope and, in the stateless and single-candidate bases, what the author's override receives.
- In `src`, the search-space-only executor rung is used by `GaussianMutator`'s executor and the nine private executors of the `Stateless*<TC,TSS>` bases. Every scope has a problem (D18 gives a search-space-only child a `NoProblem`), so it is never needed.
- Every executor `Select` and `Replace` call in `src`, Experimental, PythonInterop, samples and `origin/dynamic-Racing` passes the problem's objective. The genetic algorithm and the evolution strategy replace through the static `ElitismReplacer.Replace` and `PlusSelectionReplacer.Replace`, and the hill climber selects only through the static `BestSelector.Select`, so its executor is not affected, contrary to the 2026-11-15 entry. `MultiObjective.WeightedSum` already gives `ObjectiveDirections` a scalarizing order, so a scalarized selection is a problem whose objective is that weighted sum.
- MOEA/D needs no configured selector or replacer under a varying objective: its mating selection is uniform within a neighbourhood, and its neighbourhood update compares under a scalarization whose ideal point moves after every evaluation, which is the algorithm's own value strategy (§ 4.8).

#### Phase 7b decisions on 2026-11-19

- **D149. One executor base per role.** Each candidate role keeps only its candidate-only executor base, such as `MutationExecutor<TCandidate>`; termination keeps `TerminationExecutor<TSearchState>` and the non-generic `TerminationExecutor`, which changes the signature authors implement; interception keeps `InterceptionExecutor<TSearchState>`. Removed: `XExecutor<TCandidate, TSearchSpace, TProblem>` and `XExecutor<TCandidate, TSearchSpace>` for creation, crossover, evaluation, mutation, refinement, replacement and selection, and the three- and four-argument termination and interception executor bases, 18 types. An executor keeps what it reads from the scope, such as the problem, a search space or the objective, as its own constructor parameters, typed as what it uses, so an executor that needs only a search space names no problem. The configuration ladders, stateless bases and single-candidate bases keep their arities. Developer guidelines § 4.12 and "Explicit executors" in `operator-implementation.md` follow; the rule to use the protected `Problem` and `SearchSpace` properties instead of a captured primary-constructor parameter goes. The developer rejected the problem-bound-plus-empty alternative because an executor that does not use the problem would still name `IProblem`.
- **D150. The algorithm executor bases follow D149.** `AlgorithmExecutor<TSearchState>`, `IterativeAlgorithmExecutor<TSearchState>(interceptor)` and `WrappingAlgorithmExecutor<TSearchState>(childAlgorithm)` remain; `AlgorithmExecutor<TCandidate, TSearchSpace, TProblem, TSearchState>` and `WrappingAlgorithmExecutor<TCandidate, TSearchSpace, TProblem, TSearchState>` go, and `IterativeAlgorithmExecutor` loses its run type parameters, which only passed the problem to its bound base. Both iterative algorithm hooks declare `IterativeAlgorithmExecutor<TSearchState>` as their return type, so an iterative algorithm still cannot return an executor that skips its interceptor (§ 4.17). The configuration-side algorithm bases are unchanged. If implementation finds that something depends on the iterative executor naming the run types, it returns to discussion.
- **D151. Selection and replacement read the objective from their bound problem.** `ISelectionExecutor<TCandidate>.Select(population, count, random)` and `IReplacementExecutor<TCandidate>.Replace(previousPopulation, offspringPopulation, count, random)` take no objective. D18 stays: a problem's objective is fixed for the lifetime of the problem object. Built-in executors read `problem.Objective` at each call rather than keeping a copy, which costs nothing and leaves a later relaxation of D18 without code changes. The `Selection` and `Replacement` invocation structs, their wrapping executors, the observation executors and the composite selectors carry no objective; a composite that ranks itself, such as `EliteSelector`, holds the problem. The static helpers, such as `TournamentSelector.Select(population, objective, count, random, tournamentSize)`, keep their objective parameter, and algorithms whose objective varies use them.
- **D152. An operator that needs another objective is resolved under a problem with that objective.** An algorithm's `CreateExecutor` resolves it through `scope.For(problemWithThatObjective)`, an existing mechanism, so one problem object is the single source of the objective for everything bound under it, including children, refiners and observation records. The author writes the delegating problem, or a problem type offers a constructor taking the objective; it is created once per `CreateExecutor`, because every new problem object gets new executors that the scope retains (D18). An objective that varies during a run is the algorithm's own value strategy over objective vectors, or an operation of its own; it is not a selector or replacer argument. A separate objective beside the problem, as a scope axis or a resolution override, was rejected: see the backlog.
- **D153. No objective-replacing problem helper for now.** A `problem.WithObjective(objective)` helper would return only `IProblem<TCandidate, TSearchSpace>`, losing the concrete problem type that problem-specific operators need, and would hide capability interfaces such as `IDynamicProblem`. Deferred to the backlog until a real algorithm needs it.
- **D154. `SelectionObservation` and `ReplacementObservation` drop `Objective`.** Traces read `observation.Problem.Objective`, as the other observation records' traces already do; under `scope.For(view)` the observation's problem is the view.
- **D155. Stateless selector and replacer overrides keep receiving the objective at every arity.** Their abstract `Select` and `Replace` overrides keep today's signatures, and the base passes `problem.Objective`, so author code does not change and overrides still forward one to one to the static helpers. This follows the existing convention that the full arity receives the search space beside the problem. `StatelessSelector<TCandidate>` and `StatelessReplacer<TCandidate>` no longer implement their executor interface and build an internal executor holding the problem, instead of returning `this`; the other stateless candidate-only bases keep returning `this`.

D149 to D155 implemented on 2026-11-19 and reviewed. Removed the 18 context-specific role executor bases and the problem-bound algorithm and wrapping executor bases. Both iterative hooks return `IterativeAlgorithmExecutor<TSearchState>`. Selection and replacement executors take no objective argument and read the bound problem's objective where needed. Stateless overrides still receive the objective, and observations expose it through the problem. A resolution test uses one selector configuration under two problems with opposite objectives. No deviation from the decisions.

#### Records cleanup decisions on 2026-11-19

- **D161. What the record rule covers.** Everything a record stores and every property it has, positional, stored or computed, uses `ValueArray<T>` when it is a sequence. Method parameters and return values follow the general collection guidance: `IReadOnlyList<T>` for batches and `IEnumerable<T>` for lazy sequences, so operation methods such as `Neighborhood.Moves`, `ExpressionNode.TraversePreOrder` and the stateless operator overrides stay. Executors, which are classes, keep `ImmutableArray<T>`. Static members are not record state. Developer guidelines § 5.4 states this.
- **D162. Private lookup caches may stay.** A record may keep private lookup structures derived from its value members, such as dictionaries or arrays, when it defines its own equality over those value members only. `ExpressionTreeSearchSpace` and `WeightedIndexSampler` keep theirs. § 5.4 states the exception; wrapping such caches in another type only to pass the rule is not done.
- **D163. Stored `ImmutableArray` and arrays become `ValueArray`.** `ValidationReport.Diagnostics`, `ExpressionTreeSearchSpace.TerminalSymbols`, Experimental's `TravelingSalesmanExactSolution.Tour`, and the internal or private `OperationDraft`, `FunctionSyntax`, `WeightedSymbolSet` and `LevenbergMarquardtResult`.
- **D164. RoarNet's Turing example holds value arrays.** `TuringSolution` and `TuringOperations.Solution` hold `ValueArray<int> Tape`, and applying a move builds a new tape instead of changing the shared one; `TuringProblem` and `TuringOperations` hold transitions as `ValueArray<ValueArray<…>>` indexed by state, then symbol. The BBoB data records were migrated too and then reverted on the developer's instruction: Experimental's BBoB code keeps its arrays and its mutable `FWeierstrassData`, because experimental code need not be this strict.
- **D165. Record constructors take finite inputs as `IReadOnlyList`.** `MixtureDistribution`'s `params IEnumerable<(…)>`, `NaryExpressionNode`'s `params IEnumerable<ExpressionNode>` and the two `ExpressionTreeSearchSpace` overloads taking `IEnumerable` take `IReadOnlyList` (`params IReadOnlyList` where they were `params`).
- **D166. Observation records snapshot their batches.** `CreationObservation`, `CrossoverObservation`, `EvaluationObservation`, `MutationObservation`, `RefinementObservation`, `ReplacementObservation` and `SelectionObservation` hold `ValueArray` instead of `IReadOnlyList`, copied once per observed call, so an observer never sees a later change to a list an operator reuses.
- **D167. `Invariants` and `Requires` are value arrays.** `ISearchSpace<TCandidate>.Invariants`, `IOperatorContract<TCandidate>.Requires`, their record implementations and `OperatorContractComposition.Requires` return `ValueArray<ICandidateInvariant<TCandidate>>`.
- **D168. `SingleSolutionLayout<TCandidate>` is removed.** Its only content is a one-element enumeration, which the record rule forbids, and search states stopped being enumerable with D158.
- **D169. Mutable bookkeeping is a class.** Experimental's legacy `SymbolConfiguration`, which its grammar changes in place, and `DynamicTestFunctionProblem.State`, whose rotation matrix feeds `RotatedTestFunction.Rotate(double[,] …)`, become sealed classes.
- **D170. Test fixtures follow the rule.** Fixture records that log calls take an `Action<T>` and the test passes its own list's `Add`; fixture records holding canned outputs hold `ValueArray`, or a `Func<…>` returning the test's own batch where the test checks that a wrapper returns the operator's result object.
- **D171. Records hold values, typed as what they are.** Decided after the review of D161 to D170. A record has value semantics, so what it holds has value semantics too. The domain vectors `RealVector`, `IntegerVector`, `BoolVector`, `Permutation` and `ObjectiveVector` are sequences with ordered structural equality, so records may hold them, but only typed as the concrete vector, never as an interface such as `IEnumerable<double>` or `IReadOnlyList<double>`, whose equality is unknown. This refines D161; § 5.4 states it.
- **D172. The rule covers records that are values.** It applies to every public or protected record and to every record whose equality, hashing or serialization is used, whatever its visibility: configurations, including test fixtures deriving from operator bases, value objects, DTOs, observations and results. A private or internal record that nothing compares, hashes or serializes and that only carries values as a named tuple is exempt, and is preferred over a class there for brevity; `ExperimentRun`'s `PreparedTrial` family, `PreparedCombinedExecution` and `ScheduledExecution` therefore stay as they were. The internal and private records already migrated under D163 keep their value arrays. This amends D161.

D161 to D170 implemented on 2026-11-19. The cleanup migrated retained collections and invariant contracts to value arrays, added observation batch snapshots, and changed finite constructor inputs to read-only lists. It removed the unused layout, converted mutable bookkeeping to classes, and migrated fixtures to callbacks and value arrays. Regression tests cover Turing tape immutability and observation snapshots. The implementation follows the accepted decisions.

- **D5 construction binds the problem.** Typed scope views take the problem object; direct algorithm resolution takes it during construction, and the executor's invocation omits it. - **An observation reads the problem at its interface.** `EvaluationObservation.Problem` is an `IProblem<TCandidate, ISearchSpace<TCandidate>>`, which carries `Objective`.
- **Iteration updates need wrapped contenders.** Under `AfterEachIteration`, the epoch loop ends only if each contender applies the updates, so a contender left unwrapped makes the race spin.
- **One executor base per role and a bound objective ([phase 7b](#phase-7b-a-smaller-operator-authoring-api)).** The branch's operator and algorithm executors derive from the one remaining base of their role and keep the problem or search space they read in their own fields (D149, D150). `Select` and `Replace` take no objective (D151), so the branch's stateful replacer executors, its counting and duration advice for selectors and replacers, and `ChooseOneReplacer` drop it when they move onto the current executor contracts; its stateless selector and replacer overrides keep it (D155). `RandomImmigrantGeneticAlgorithm` calls only the static `ElitismReplacer.Replace`, which keeps its objective.

### Phase 4 fork compatibility inspection

Inspected the local remote-tracking `origin/dynamic-Racing` at `c35ebf82062c78b3d8269892632ee7ed0adfdce1` on 2026-11-11; this is a source inspection, not a merged or executed compatibility test.

- `ResolutionScope.CreateForkedScope()` calls `state.Fork()` and retains the original parent and observation context. `State.Fork()` rejects construction in progress, creates a peer state with the same ancestor, copies only local factories whose target implements `IForkableFactoryPreparation`, and memoizes each copied delegate by reference. Non-forkable local factories and advice factories are prepared afresh; ancestor state stays shared.
- `ExecutionFactory.Forkable` separates persistent state from execution bindings: its copy function copies the state, and its binding function constructs fresh executions and resolves fresh child bindings. For example, `DynamicRateMutator` copies `SourceProblem`, `LastObservedEpoch` and `RemainingResponseCalls`, then binds a child mutator through the supplied scope. Current executors own both private data and resolved child references. Copying their table references would share mutable state; constructing replacements without a snapshot would lose the learned state. An executor snapshot contract and child rebinding therefore remain merge work, not a feature phase 4 delivers.
- `WithContext(context)` retains prepared state while replacing the observation context through `context.WithState(state)`; existing executions keep their children and advice, and resolving again rebuilds those bindings. Racing's `Entry.Restart` uses this before placing the new race's performance callback. Current repeated resolution returns one executor per configuration reference in its owner, with wrappers already in the graph. Changing that graph does not rebind an existing executor or its callback. The merge must reconcile contender restart tracking, configuration reference identity, explicit sharing and retained executor children; this inspection does not accept a second resolution mechanism.
- The branch's fork predates run-bound `RunResults`. Child scopes in this branch share one result table and stopwatch, and result nodes can live in the root executor table. A peer child fork still needs to preserve the run's results and D29's precise sharing guard without treating published results as private snapshots. Root forks additionally need an explicit result-ownership decision: copying live entries or a `RunResults` reference would couple independent runs and retain the original root used for result lookup. No root-fork result policy is implemented or implied here.
- Signature checks remain on every typed `Resolve` (D61), including contenders created by `AlgBuilder`; declared-child preflight and `ChildExecution` mappings remain intact. Tree-wide construction failure remains D62. Fork integration must preserve those contracts as well as the branch's rule to fork only between invocations. D63 removes hidden timing wrappers and leaves the scope responsible for neither root timing nor overlapping-call accounting.

The scope's executor table, parent links and sharing ownership remain usable foundations for integration. Factory snapshots and observation-context rebinding cannot be merged mechanically. No fork implementation or compatibility guarantee is claimed.

## What does not simply disappear

The reports describe this design as removing rules. These stay in another form:

- **A clock ticks once, and before the observations that read it.** Before phase 3 this was advice deduplication with closest-occurrence ordering. Since phase 6 a trace lists its clock placements after its recording, and one `CreateRun` analyzer list or `Substitute` call applies a shared substitution once, at its last position ([D100](#phase-6-decisions-after-the-design-pass-on-2026-11-17)). A clock that only reads, such as `Clock.Elapsed`, needs no placement. Placing at the original reference would be wrong for a second trace on the same target: it would sit inside the first trace's counter and read the clock before that call was counted. Within one call D28 settles it through the listed order, with the clocks after the traces. Each call places what it lists, so a clock shared across separate calls ticks twice ([D36](#decided-in-round-21)). Since [D103](#phase-6-decisions-on-2026-11-18) no trace places a clock ([D110](#phase-6-step-3-decisions-on-2026-11-18)): a trace lists the counter's clock, `counter.Clock`, and the caller lists the counter's `Counting` substitution, or a clock that places itself, after the traces that read it. The rule stays the listed order, and a clock placed once ticks once however many calls place the traces.
- **Persistence.** A substituted graph is persistable only if the wrappers it adds are data. `Trace(observation => ...)` holds a delegate, so instrumented graphs stay under the documented exception until [value strategies](developer-backlog.md#runs-execution-and-experiments) exist for them. `Duration` holds a `TimeProvider` until [D103](#phase-6-decisions-on-2026-11-18) moves time to the run; afterwards counters, durations and the library's clocks are data, except the epoch clock, which keeps its live problem as a documented exception ([D107](#phase-6-step-3-decisions-on-2026-11-18)). Substitutions themselves are never persisted ([D101](#phase-6-decisions-after-the-design-pass-on-2026-11-17)): what is persisted is the configuration a substitution produced, and a caller who also wants the configuration without instrumentation persists it before substituting, and `CreateRun` places analysis for one run without changing the configuration. Analyzers and shared nodes still need an identity in a persisted form.
- **Reach.** Advice reached anything resolved below it, including configurations a delegate creates at run time. A substitution reaches only declared children (D3). It also changes only the graph it returns. Before phase 3 a budget counted every call of its operator in its scope and child scopes, including a direct request for the original algorithm (`DeferredAlgorithmResolutionTests.cs:294`), and the budget and that request used one algorithm executor (`ConfigurationSharingTests.cs:118`). With eager substitution the budget holds a copy of the algorithm, so a direct request for the original neither counts nor shares that executor. This follows from D1. Analyzers passed to `CreateRun` target the budgeted graph, so a named source comes from the configuration the run receives ([D95](#phase-6-decisions-after-the-design-pass-on-2026-11-17)).
- **Declaration cost.** Avoiding reflection means every configuration author declares parameters, and a declaration can be forgotten. Analyzers in `analyzers/` are `IsPackable=false` with `PrivateAssets=all`, and the project files contain no packing entry, so external authors do not get a completeness analyzer today (D2). The developer accepts this for now. Its overhead is to be measured, and the mechanism designed in more detail, before the choice is final.

The clock order above was settled in [round 21](#decided-in-round-21).

## Open decisions

### Decided in round 1

Decided by the developer on 2026-11-05.

- **D1. A substitution happens eagerly,** before the run, so that the configuration the caller holds is what runs. An intent node that expands when built is not used. The developer confirmed this in round 2. A copy such as `budget with { Algorithm = other }` therefore loses the counter on the new child, so the budget never triggers. Reporting that is a candidate for the [configuration graph check](developer-backlog.md#scenarios-awaiting-a-concrete-need).
- **D2. Parameters are declared by hand for now.** The detailed design, after the overhead is known, decides whether a completeness check, analyzer or generator is added. Metadata is mechanical, unlike the [generated operator families](developer-backlog.md#generated-operator-families) rejected earlier, so a generator would need a fresh explicit decision, and an analyzer or generator must ship in the NuGet package so that external authors are not disadvantaged. The risk to weigh: a forgotten child declaration makes a predicate substitution skip that subtree silently, while a placement by reference fails loudly.
- **D3. Sequential substitutions are deterministic, and a substitution stops at delegates.** The output of the first substitution is the input of the second. A substitution reaches declared children, including a Cycle's inner algorithms. It does not look into what a delegate creates, such as racing's `AlgBuilder`, and whoever writes the delegate can call `Substitute` inside it. An outer trace then stops reaching contenders automatically, so Bernhard Werth's `origin/dynamic-Racing` is affected and should be consulted first.
- **D4. Executor controls are replaced in phase 5.** `MutationStrength` is an explicit configuration node, not an operator, and is given to both the mutator and the strategy. See [the proposal](#executor-control-proposal).
- **D6. The design rules are in [developer guidelines](../docs/contributing/developer-guidelines.md) § 2.5,** aligned with §§ 2.1, 2.4, 3.1 and 3.6 instead of repeating them. Rule 5 was folded into those sections. See [the rules](#adopted-design-rules).
- **D7. The proposed statuses of ideas 7, 8, 9, 10, 11, 13, 14, 17 and 18 are accepted,** as the [status table](#idea-status) shows.

### Decided in round 2

Decided by the developer on 2026-11-05.

- **D9. A substitution target inside a shared configuration is a wrong configuration.** A budget targeting `evaluator` inside a shared `cached` produces a private copy of the cache. Report a `Sharing` entry that its subtree never uses only if that stays one walk over declared parameters with no new mechanism. Otherwise leave it to the [configuration graph check](developer-backlog.md#scenarios-awaiting-a-concrete-need).
- **D13, the settled names.** `Analyzer` stays, and it replaces `Instrument`, which the glossary already uses to define it. `Instrument` keeps its name until the type is removed. `Fits` becomes `Supports`, as § 8.13 suggests and `SupportedExecutionDescription` already reads, because `Fits` is easy to confuse with scikit-learn's `.fit`. `Rewrite` is the wrong word; see [D13](#decided-in-round-5).
- **D14. Selection has a core version and extensions.** The core does the main work, and extensions cover common patterns. Which patterns get extensions is decided during implementation.
- **D16. An unset `Strength` slot means no adaptation.** Detecting a shared mutator with an unshared strength stays out, because it would complicate things too much. See [the proposal](#executor-control-proposal).
- **D17. Several substitutions at once.** Nothing stores pending substitutions, because a stored list would rebuild the aspect list. One call may take several, which apply one after another (D28). A substitution copies every ancestor of what it changes, so within one call a node stays itself for matching while only its children change. With `ga.Evaluator = Cached(E)`, `ga.AnalyzedBy(countE, best)` therefore works, although the first substitution copies `Cached` and `best` targets the original. `GenealogyAnalyzer` needs this too, because it hooks operators and the algorithm containing them. Separate calls carry no such memory, so `ga.AnalyzedBy(countE).AnalyzedBy(best)` no longer finds `Cached`. A placement by reference that matches nothing is an error naming the target and any delegate boundary it could not enter, while a predicate that selects nothing returns the same instance.

Decided by the developer on 2026-11-05.

Their executors resolve through that interface and `Algorithms` has no setter, so the parameter only gives typed reads such as `cycle.Algorithms[0].Terminator` (`InferenceConstructionSpecs.cs:152-158`). ### Decided in round 4

Decided by the developer on 2026-11-05.

- **D13, what leaves the API.** `Aspect` goes.
- **D18. A meta-algorithm gives a child another problem through a view.** `scope.For(problem)` returns a view of the same scope, as today's typed views do. The developer pointed out that a child scope would break default sharing: child scopes build independent executors, so one `MutationStrength` used by both children would silently become two. A scope decides lifetime and a problem decides binding, and the two stay separate. The code already separates the view from its storage: each public `ResolutionScope` holds a private `Node` that contains the table (`ResolutionScope.cs:18,241`), so no new concept is needed. Search space and objective stay fixed for the lifetime of a problem object, and a different search space means a different problem object. An operator executor is not shared across problems, which the developer accepts for the regular case. If an operator's private data must survive a change of problem, that case uses one dynamic problem instead, and gives up the assumption that the problem stays immutable. See [the conditions](#problem-bound-executor-conditions).
- **D19. ### Decided in round 7

### Decided in round 10

Decided by the developer on 2026-11-05.

- **D33. The overload taking a configuration also takes an equality comparer.** This follows the .NET convention of `Contains(value, comparer)`. `Substitute(target, replace, comparer)` and `Substitution.Of(target, replace, comparer)` select every reachable node the comparer considers equal to the target, and unlike a predicate they report an error when there is none. `ReferenceEqualityComparer.Instance` and `EqualityComparer<IConfigurationNode>.Default` work as they are. ### Decided in round 11

Decided by the developer on 2026-11-06.

- **D33, the default. Leaving out the comparer means reference equality.** A user who supplies an operator means that exact object, and a user who wants another notion asks for it. The parameter is optional and `null` means reference equality, because `ReferenceEqualityComparer.Instance` is not a constant and cannot be a default value, so the documentation has to state it. This differs from the usual .NET default on purpose. Slots left at their defaults are value-equal even in differently configured algorithms, so with value equality `cycle.Counting(gaA.Evaluator, out var c)` would also count `gaB`'s evaluator, which the current reference matching rules out on purpose (`Pointcut.cs:12`, `PointcutTests.cs:8`). Shortcuts such as `Counting` therefore always match by reference. In a predicate, `op == x` is a reference comparison when `op` is typed by an interface, which is the usual form under D20, because a record's `==` is defined on the concrete record. C# warns only when one side has a concrete type (CS0252). Value equality in a predicate takes `op.Equals(x)` or a parameter typed by the concrete record. The comparer form also reports an error when nothing matches, which a predicate does not.

- **D32. A reference that an earlier call copied stays an error, and the pilot adds nothing for it.** Under reference equality (D33), a reference stops matching once an earlier call copied it. A substitution copies only the path from the root to what it changes, and every other slot keeps its reference. `ga.Substitute(ga.Mutator, ...).Substitute(ga.Evaluator, ...)` therefore works, because `ga.Evaluator` is still in the copy. Naming the same wrapped node again, or something inside a wrapped node, works too. A name fails when something below it changed: `ga` and `ga.Iterations` after any change, because the receiver is an ancestor of every node, and `ga.Evaluator` after a change to `E` when that slot holds `Cached(E)`. A node replaced completely also fails, rightly. Every failure is the error D17 requires and never a wrong graph, and the reverse order builds the same graph. The realistic cases are an algorithm boundary after an operator hook, a hook after a budget and a nested algorithm. Which references go stale depends on the shape of the graph and on what ran before, which is the temporal coupling the developer guidelines say to try to remove (`developer-guidelines.md:71`). Reference matching guards this coupling and does not remove it, which the developer accepts for now to keep the design simple.

  The error names the three routes that already exist. One call resolves every target against the same input (D17), which keeps D17's map from copy to original for the length of the call, and a boundary on the receiver itself needs a receiver typed by the interface (D10). Ancestors first works whenever the ancestor is wrapped rather than replaced. Naming the target from the current configuration, as in `a.Counting(a.Iterations, out var i)` or `limited.Counting(limited.Algorithm.Iterations, out var i)`, works as far as typed slots reach. It names what is there now, so naming `a.Mutator` gives `Timed(Counted(M))` where `ga.Mutator` gives `Counted(Timed(M))`. An analyzer names its targets when it is created, so `ga.AnalyzedBy(countE).AnalyzedBy(best)` on `Cached(E)` takes one call or the reverse order.

  The pilot's budget and `ga.Counting` show whether these routes are enough. If they are not, a selector such as `.Substitute(g => g.Mutator, ...)` is the first addition. The developer likes the form and it compiles against a stub, but every shortcut would need it too, it needs a cast to pass an interface-typed slot, and it does not help an analyzer. A comparer for "equal once added wrappers are ignored" remains possible after that, with no new overload because D33 gives it a place. It bends the comparer contract, because that rule compares in one direction, it also selects an equal twin, and shortcuts could not use it. The [rejected alternatives](developer-backlog.md#finding-a-configuration-copied-by-an-earlier-substitution) are in the backlog.

### Settled in round 17

A review of the staged pilot on 2026-11-06 found these in the new code. It found nothing in substitution ordering, reference lists, parameter dispatch, observation forwarding or the HLib0003 change. The first and third were confirmed by failing tests before the fix.

- **One lock for results and construction.** Creating a result that read a configuration's result took the two locks in the opposite order from building a configuration that read a result, and that deadlocked. `RunResults.Sync` now guards both tables. The cost is that a live `run.Result` waits while a turn builds its executors, which a read of a configuration's result already did.
- **A cold read has the recursion guard.** A configuration that read its own result overflowed the stack, and now gets the recursive construction error. The read does not check for failure, because the results of a failed run stay readable, also one never built.
- **The configuration decides ownership of its result.** `IConfigurationNode` is covariant, so deciding from the requested type gave a `Counter` held as `IConfigurationNode<IExecutor>` a second count per scope. `Owner` now asks the configuration, which also removes its `bool` parameter.
- **Stable substitutions under concurrent reads.** Twelve copies of `field ??=` could hand out different instances, and a shared clock would then count twice in one call (D28). The base class now caches atomically, so authors write `CreateSubstitutions` and cannot get this wrong. A public `Substitutions` stays what callers read.
- **D29, what a read does.** A read of a run result does not count as resolving it. The review proposed that it should, but `run.Result(budget.Counter)` before `Complete` would then make a budget at the root fail with "cannot be shared", and a read must not break a run. The accepted consequence is that an external run result with children, read before a root-level `Share`, keeps the executor it was first built with instead of one in its own child scope. An accumulator has no children, so it is unaffected. The developer accepted this.
- **Not changed.** A cold read whose hook catches a nested construction failure can still publish its result. Results of a failed run stay readable by design, and nothing resolves through that result afterwards.

- **D49. `CreateExecutor` moves to a new `IOperator<TCandidate>`.** The hook names no operation, so `IOperator<TOperation, TCandidate>` inherits it, and a configuration has one however many operations it performs. Separate hooks per operation become compile errors, CS0539 for explicit ones and CS8705 for inherited defaults, which replaces the run-time check in `ConstructionHooks` and its inspection of a type's interfaces and methods. Slots keep naming the operation. Accepted costs: authors see a compiler error rather than the library's explanation, explicit hooks change their syntax, and a configuration can again implement one hook per candidate. `Resolve` rejects a second candidate its executor does not serve, but an executor serving both is built by whichever candidate is requested first, with no error. A derived type adding an operation to its base's hook compiles too, and fails at resolution if that executor does not serve the operation.
- **Reflection stays out of program logic.** The developer does not want code that inspects types and lists their methods or interfaces. `typeof` of a concrete type and `IsAssignableTo` are fine, and so is reflection that only builds a better exception message, which keeps `ProducedSearchStates` and `ExecutionSignature.Name`.

- **D50. `SettingParameter<TOwner, TValue>` amends D45.** `Parameter` decides on the closed type, so a value typed by a type parameter is read as a child, or rejected as a list, when it closes over a configuration, although it is data. A terminator stopping at a target candidate is a legitimate case of this. `SettingParameter` is never entered and never reported, whatever its type closes over. It is used where a value is typed by a type parameter, so 3 declarations use it: `PredefinedCandidates` and the two `SourceProblem` values. The other declarations stay `Parameter`, so a concrete setting can be written either way. Accepted limits: `Parameter<X, TCandidate>` still compiles and is silently a child when closed over a configuration, which the later analyzer is to report, and a delegate in a `SettingParameter` is not reported as a boundary.
- **A record never holds or declares an `IEnumerable`, generic or not.** A sequence has no value semantics, which breaks the idea of a record. The developer rejected `IEnumerable<TCandidate>` as the declared value of `PredefinedCandidates`, and the rule is in the [developer guidelines](../docs/contributing/developer-guidelines.md).

### Decided in round 21

Decided by the developer on 2026-11-08, after two independent reviews of the draft and a further review of how analyzers are used. It replaces the seven-step list of phase 3, so earlier references to step 6 now mean the deletions spread over steps 1 to 5.

Analysis:

- **Why placement had traps.** Each separate `Substitute` call is its own rewrite, with its own wrapper order and its own copies of the graph. Advice never had this, because it was matched once at resolution. Analysis therefore happens in one rewrite where it can, and several rewrites are made safe rather than relied on. A substitution stays a pure function of the graph and its arguments.
- **D25. One form for every measurement: define on the source, attach once, read from the run.** This replaces the two-protocol draft in which counters could only come from `Counting(..., out)`.

  ```csharp
  var evaluations = ga.Evaluator.Invocations.CountCandidates();
  var best = ga.Evaluator.Invocations.TraceBestSoFar(clocks: [evaluations]);
  var quality = ga.Iterations.TracePopulationQuality(clocks: [evaluations]);

  var run = ga.AnalyzedBy(best, quality).CreateRun(problem, random);

  run.Result(quality).By(evaluations);
  run.Result(evaluations).CurrentCount;
  ```

  `AnalyzedBy(params)` is one `Substitute` call, so every target is matched against the graph that call received, and nothing named on that graph can go stale within the call ([D58](#decided-in-round-21) covers an earlier rewrite). A trace attaches its clocks itself, listed after its own placement so that they sit closer to the node. One object stamps, is read and can be limited. `Counting(target, out c)` stays as the same thing in one step, returns the same `Counter`, and serves count-only use and terminators, where it cannot be forgotten. `Trace*` stays on sources. This settles D15: a definition keeps its source, because that is how it places itself. A `Counter` stays a sealed class (D39). One created from a source holds its placement privately, outside its declared parameters, under the analysis exception of § 4.8. Custom clocks keep working through `IClock.Substitutions`. The cost is the two-step form the developer doubted, which D57 makes safe. Superseded in part by [D103](#phase-6-decisions-on-2026-11-18) on 2026-11-18: a counter or duration no longer comes from a source or places itself, a source returns the substitution that places a counter the caller supplies, and a trace places none of its clocks.

- **D58. One operation means one `AnalyzedBy` call, made first.** The existing form stays: one call taking several substitutions, applied one after another (D17, D28). A budget or `Counting` before it copies `ga`, so `ga.Iterations` then gives D32's error, while `ga.AnalyzedBy(best, quality).LimitedToInvocations(ga.Mutator, 100)` works because the mutator's reference survives. The documentation says "analyze first, then budget", and D32's error names that route. A generalized call that also takes budgets and wrappers is a [backlog item](developer-backlog.md#runs-execution-and-experiments), and steps 1 and 3 count how often budget-then-analyze occurs as its trigger. A simultaneous pass that orders wrappers by kind is [rejected](developer-backlog.md#analyzer-placement-alternatives-rejected-on-2026-11-08).
- **D36. No clock rule: each call places what it lists.** Analyzer placement is an ordinary `Substitute`, and a clock has no special position. One call lists the clocks after the traces (D28), so a shared clock ticks once and before them. A clock shared across separate `AnalyzedBy` calls ticks twice, as `T1(C(T2(C(O))))`, and a trace on the original `m` after `Counting(m, out c)` gives `C(T(O))` and reads `c` before the call. D58 already asks for one `AnalyzedBy` call per operation; the second case traces `counted.Mutator` instead, or creates the counter from the source and analyzes first. Revised on 2026-11-08 during step 1, which first built a look-through rule; [the backlog](developer-backlog.md#analyzer-placement-alternatives-rejected-on-2026-11-08) records why it went. Observers commute under the observation contract, so most `Advised(a, b)` order reversals (D28) change no assertion. Amended by [D103](#phase-6-decisions-on-2026-11-18) on 2026-11-18: no trace places a clock, so the caller lists a clock's placement after the traces that read it, and a clock shared across separate calls ticks once, because only its own placement places it.
- **D57. Forgetting to attach is an error on read.** `run.Result(x)`, for a definition that knows a placement, walks the run's declared graph for a parameter holding `x` by reference, through `GetParameters` and `GetValue`, so authors declare nothing beyond their parameters. If there is none and the walk crossed no delegate slot, it throws. An unvisited Cycle branch is still found and reads 0, which is true. A closure such as AutoEC's sits behind a delegate and is not checked. Failed runs behave the same. A discarded `AnalyzedBy` result is caught as well. Internal lookups, as from a trace's `CreateResult`, are not checked. Known limits: an undeclared child is a leaf, and a terminator holding a never-attached counter still never stops, so the documentation uses `Counting(..., out)` there. Instrument analyzers need no node form for this. Amended by [D103](#phase-6-decisions-on-2026-11-18) on 2026-11-18: counters and durations expect no placement, so the check applies to configurations that place themselves, analyzers and clocks that observe ([D110](#phase-6-step-3-decisions-on-2026-11-18)); a counter placed nowhere reads zero, and a placing substitution whose target the graph does not hold fails when it is applied (D17).
- **D59. `Substitute` takes substitution bundles, and `AnalyzedBy` only names it.** Decided by the developer on 2026-11-10 during step 2, when `Count()` stopped returning an instrument and `AnalyzedBy(params IReadOnlyList<Instrument>)` could no longer take a counter. A substitution bundle is a flat, ordered list of substitutions that belong together; `ISubstitutionBundle` (working name) in `Execution` has one member, `Substitutions`. A single `Substitution` is a bundle of one, and `Instrument`, `IClock` and with them `Counter` and `Duration` are bundles of their placements, so analysis builds on substitution rather than the reverse, and one call can mix traces, counters and plain substitutions. `AnalyzedBy` takes bundles too and adds nothing but typing the result by the receiver's interface, which an analyzer of the receiver itself needs. Rejected for now, with their triggers in [the backlog](developer-backlog.md#scenarios-awaiting-a-concrete-need): a composite bundle, and an `IAnalyzer` on top, which would be an empty marker in the wrong layer. A first draft named the interface `IAnalyzer` and made `Substitution` an analyzer, which turned the dependency around. `Instrument` gets no further design, because phase 6 retires it. Superseded in part by [D103](#phase-6-decisions-on-2026-11-18) on 2026-11-18: counters and durations are not substitutions, and a clock is one only when it needs placement, which the caller then lists ([D110](#phase-6-step-3-decisions-on-2026-11-18)).

## Proposals behind the open decisions

### Executor control proposal

The strategy and its mutators name one explicit adaptation node. The base strength remains plain configuration data; the adaptation holds a scale factor at runtime.

```csharp
var adaptation = new ScaleAdaptation();
var gaussian = new GaussianMutator(0.5, 0.1)
{
    MutationStrengthAdaptation = adaptation
};
var strategy = new EvolutionStrategy<RealVector>
{
    Creator = creator,
    Mutator = gaussian.Timed(duration),
    MutationStrengthAdaptation = adaptation
};
```

```csharp
// Fresh adaptation each turn by default; retain it across turns explicitly.
var cycle = CycleAlgorithm.Create(strategy, other).Sharing(adaptation);
```

Both the mutator and strategy resolve the adaptation through the ordinary scope. `ScaleAdaptation : Adaptation<AdaptedScale>` creates a runtime factor initially 1. `IAdaptation.Apply(baseValue)` reads the effective value, and the strategy's 1/5 success rule multiplies `AdaptedScale.Factor`. An `OffsetAdaptation` similarly creates an `AdaptedOffset` with a settable `Offset`, for other rules. External nodes can implement `IConfigurationNode<IAdaptation>` directly. The read slot accepts every form; the strategy's write slot names `ScaleAdaptation`. Wrappers forward nothing, and several mutators adapt together by naming the same link. Observing adaptation values is deferred to the backlog ([D81](#phase-6-questions-after-the-review-on-2026-11-16)).

Decided details (D16, amended 2026-11-16):

- **An unset strategy slot means no adaptation.** A Gaussian mutator with no link uses its configured base unchanged. Strategies naming Gaussian mutators must opt in explicitly; factories take no adaptation argument.
- **Share the adaptation whenever the mutator is shared or its value must survive a turn.** Sharing a configuration shares its children only when they are shared too.

  | Shared on the Cycle     | Effect                                                                                    |
  | ----------------------- | ----------------------------------------------------------------------------------------- |
  | Nothing                 | A fresh adaptation each turn; mutator and strategy agree                                  |
  | `adaptation`            | The value survives turns; mutator and strategy agree                                      |
  | `adaptation`, `mutator` | Adaptation and mutator private data survive turns; both agree                             |
  | `mutator` only          | The mutator reads its original adaptation; each strategy writes another that nobody reads |

  No detection is added. Documentation and tests cover this case; a later configuration graph check may report it.

- An adaptation the mutator does not read is left to that same later check.

### Problem-bound executor conditions

Direction favored; decided from the [phase 4b spike](#phase-4b-problem-binding-spike) (D5). The developer's proposal resolves the conflict recorded earlier, that an executor bound to one problem cannot keep its state across a switch: the executor stays bound to one problem object while that object changes underneath, so state survives. [`DynamicProblem`](../src/HeuristicLib.Experimental/Problems/Dynamic/DynamicProblem.cs) already works this way. Its objective and search space are fixed at construction, its environment advances through `Update()`, and a reader/writer lock keeps one evaluation in one environment.

Findings on 2026-11-05, by text search:

- About 111 signature lines in `src` and 107 in `test` carry the `random, searchSpace, problem` parameters. About 12 operator files read a member of the problem, 7 of them in core, mostly `Objective` and `Evaluate`.
- No `problem with` or `searchSpace with` exists in `src`. One operator caches instance data: `DynamicRelativeQualityEvaluator` keeps its source problem and a best-known objective vector, which it refreshes by epoch (`DynamicRelativeQualityEvaluator.cs:68-73,91-95`). It already meets the condition on epochs below, and needs its reference check (`:85`) only because it is not bound to the problem.
- Three kinds of operator call children with another problem: racing's meta creator and mutator (`DynamicRacingAlgorithm.cs:130,276`), the composite search space's parts (`CompositeSearchSpace.cs:55-56`), which pass a `NoProblem` carrying only the part's search space, and two inner-problem refiners in PythonInterop (`PythonInterOptEquationScoring.cs:26`, `ExtendedSymbolicRegressionProblem.cs:40`).

The developer requires that funneling a different problem or search space to a child stays supported, for algorithms and operators alike, and that a meta-algorithm does it while constructing executors. The scenario to support is a problem-specific meta-algorithm that decomposes a Traveling Thief problem into a tour and a packing subproblem, each with its own search space and genotype, solved by inner algorithms, together with composite search spaces and genotypes. Proposed shape, not implemented:

```csharp
protected override IAlgorithmExecutor<...> CreateExecutor(ResolutionScope<TravelingThiefProblem> scope)
{
    var tourProblem = new TourProblem(scope.Problem);       // a separate problem object with its own search space
    var packingProblem = new PackingProblem(scope.Problem);
    return new Executor(
        scope.For(tourProblem).Resolve(TourAlgorithm),      // a different genotype follows from the child's problem
        scope.For(packingProblem).Resolve(PackingAlgorithm),
        tourProblem, packingProblem);
}
```

If a subproblem's quality depends on the other part's current solution, the meta-algorithm updates its subproblem between turns. That is the mutable problem again, with the meta-algorithm as its owner, and inner state survives. Building a new child per turn stays possible but starts fresh unless the state is shared.

A design must settle these points:

- **Truly problem-specific operators stay first-class,** such as planned vehicle routing operators that read instance data. A typed problem at construction replaces the generic call argument.
- **What may change under the hood.** Recommended (D18): instance data only. Search space and objective stay fixed for the lifetime of the problem object, as in `DynamicProblem`, because a population would not stay valid across such a change. A different search space means a different problem object at construction.
- **Executors bind to the problem object, not to values read from it.** Values derived from a problem that can change are not cached, or are checked against its epoch.
- **When a switch takes effect.** Recommended: the guarantee `DynamicProblem` already gives, that one evaluation is scored by one environment. Qualities already in a population become stale, which `ReevaluationInterceptor` handles for dynamic problems today.
- **Independent trials.** A mutable problem shared across trials makes them dependent. As with dynamic problems today, the caller owns this.
- **Scope.** `scope.For(problem)` is a view of the same scope, not a child scope (D18). The search space always comes from the problem, and a child that only needs a search space gets a `NoProblem` as today.
- **Default sharing across problems.** Today a scope holds one executor per configuration (`ResolutionScope.cs:191`). Proposed: an operator or algorithm has one executor per configuration and problem, because an executor is bound to one problem. A node whose hook receives a plain scope, such as a strength or a counter, cannot read a problem and has one runtime object per scope, whichever view asks. Same configuration and same problem therefore behave exactly as today, and problems are compared by reference.
- **`Sharing` across problems.** `Sharing` and Cycle turns change lifetime only, and the same rule applies inside them. A shared strength stays one across subproblems. A shared operator requested for another problem gets its own executor bound to that problem, so it never uses the wrong problem. The cost is that two subproblems do not share an operator's private data, which the developer accepts. Data meant to cross belongs in a node with a plain hook, or the case uses one dynamic problem instead of two problems.
- **Authoring.** A stateless operator cannot be its own executor once it needs the problem or search space. A base class can keep today's one-method override and allocate a small bound executor per build, so the author's call site stays as simple. This means the authoring ladder of §§ 8.4 and 8.5 does not vanish completely; the executor generics and typed scope views do. Allocation per build must be benchmarked.
- **`Fits`.** A bound build checks the problem type when it asks for it. Whether a separate pre-flight check remains depends on `TryResolve` and on validation reaching children that a run builds later.
- **Cost.** Every operator changes, which is why the spike comes before any migration.

Nothing in phases 1 to 4 prevents or requires this, except that typed scope views and arity ladders stay until it is decided.

### Adopted design rules

Applied as developer guidelines § 2.5, with a pointer from the `AGENTS.md` architecture checkpoint:

1. **Express before building.** Write a new scenario with existing nodes and rules first. Propose a new mechanism only when that is not reasonably possible, and state which existing mechanism it makes redundant.
2. **One composition mechanism.** Behavior is added by nodes and conveniences generate nodes. No new mechanism changes an executor after construction.
3. **The executor graph follows from the configuration graph and the problem.** No new dependency on anything else, such as attachment order or request context, without a recorded decision.
4. **Define errors out of existence.** A new guard is a signal of temporal coupling to remove, not a fix.

The rules are phrased as limits on new work, because advice still exists until phase 3. A fifth proposed rule, on keeping the concept count deliberate, is covered by §§ 2.1 and 3.1 and was folded into a sentence in § 2.5.

Not adopted from the reports: a fixed numeric concept budget, and "three production users" as a reason to remove something, because in-repo usage says nothing about external consumers. Three users may still be asked of a newly proposed generic mechanism.
