# Migrating `dynamic-Racing` onto `core-simplification`

`origin/dynamic-Racing` (at `c35ebf82`) merges `core-simplification` and migrates its own code; this branch does not change it. The merge base is `a2643bc1`. Since then the racing branch has 7 commits that touch 74 files, and `core-simplification` changed about 459 files under `src`. That includes the operator unification, which replaced the role interfaces, execution factories and aspects the racing branch still builds on. Backward compatibility is not a goal: migrate every caller, and add no shims or `[Obsolete]` members.

This file is the complete handover. It names decisions by their label, such as D5, and states what each one says, so the reader needs no other plan. The current rules live in the [developer guidelines](../docs/contributing/developer-guidelines.md), the [operator implementation](../docs/contributing/architecture/operator-implementation.md) and [execution resolution](../docs/contributing/architecture/execution-resolution.md) pages, the [layering](../docs/contributing/architecture/layering.md) page and the [glossary](../docs/guide/glossary.md).

In this file, `branch:` paths and line numbers refer to `origin/dynamic-Racing`; linked paths refer to `core-simplification`.

## Reference port on this branch

This branch already ports racing as it stood at the merge base. Use it as the working example.

- [`DynamicRacingAlgorithm.Entry`](../src/HeuristicLib.Experimental/Algorithms/DynamicRacingAlgorithm.cs) (lines 377 to 441) builds a contender's tracked graph once, `algorithm.ApplyingIterationUpdates().Substitute(evaluator.Invocations.Observing(callback))` (lines 393 and 394). Each start or restart then resolves that graph in a fresh child scope and streams it with `RunStreaming` (lines 436 to 440). Executor state lives in the executor's fields (lines 167 to 171).

  - `ATraceOfContenders_IsPlacedInTheBuilder`: an outer substitution reports `AlgBuilder`, and a trace placed inside the builder records every contender into the run's one trace.
  - `NewExecutorStartsIndependentBurnInWhilePausedExecutorKeepsProgress` and `ContendersOfOneAlgorithm_EachBuildTheirOwnExecutor`: executor lifetimes of contenders.
- [`DynamicAnalysisTests`](../test/HeuristicLib.Tests.Experimental/Problems/Dynamic/Analysis/DynamicAnalysisTests.cs) covers `ApplyingIterationUpdates()`: `AfterEachIterationPolicy_UpdatesAtTheIterationBoundaryOfTheWrappedAlgorithm`, `IterationUpdates_AreAppliedBeforeTheStateIsYielded`, `IterationUpdates_AreNotAppliedAfterTheStreamIsDisposed` and `IterationUpdates_SupportOnlyDynamicProblems`.
- [`AutoEcPaperScenarioTests`](../test/HeuristicLib.Tests.Scenarios/Problems/Dynamic/AutoEcPaperScenarioTests.cs) is this branch's migration of the scenario file that the racing branch moved to `Papers/AutoEC`. `DynamicRacingGa_OnMovingPeaks_ProducesPaperExperimentSignals` shows how to place analyzers on an evaluator that `AlgBuilder` captures. Do not copy `DynamicRacingGa_OnActivatedTsp_UsesPaperLikeScenario`: it calls `racing.Substitute(qualityCurve)` and passes `[bbcp]` to `CreateRun`, which D3 rejects because the evaluator sits inside `AlgBuilder`. The test passes only because it returns early when the local Concorde files are missing.

## Behaviour to keep in mind

- **Construction binds the problem (D5).** A resolution scope holds one executor per configuration and problem reference pair. The problem object is given at resolution, the executor keeps it, and its role calls omit it. A dynamic problem stays one object that changes underneath, so an executor's state survives epochs but not a new problem object.
- **Executor state lives as long as its executor.** Resolving again in the same scope returns the same executor, so `DynamicRateMutator_RebindingPreservesRemainingResponseCalls` still holds within one scope. A new child scope builds new executors with fresh state, which is what this branch's racing does at every restart. The racing branch keeps state at the factory, inherits it into challengers through forking and retains it across races through `WithContext`. Nothing here does that; see open point 1.
- **Lifetimes of the racing entries differ.** This branch creates a new entry, and with it a new tracker, for every contender in every race; the tracker spans the iterator restarts within that race. The racing branch reuses the incumbent's entry across races (`branch:…/DynamicRacingAlgorithm.cs:229-238`) and gives it a new `ContenderPerformance` in `Restart` (`branch:…:452-464`). A new performance object needs a new tracked graph built from it, because the callback is part of the graph.
- **`AlgBuilder` keeps receiving the untracked algorithm.** Challengers are built from `entries[0].Algorithm` (`branch:…/DynamicRacingAlgorithm.cs:170`, this branch line 188). Keep `Entry.Algorithm` as what the builder returned, and keep the tracked graph private, or the incumbent's tracking leaks into challengers. `TheBuilder_ReceivesTheAlgorithmItReturnedWithoutTheTracker` pins this.
- **An outer substitution does not reach contenders (D3).** A substitution stops at delegates such as `AlgBuilder` and `EvaluatorSelector`. A target named by reference reports the delegate by name, and a selection by type or predicate passes over contenders without an error. Place analyzers inside the builder, or on a shared operator before the builder captures it. The [developer backlog](developer-backlog.md) records this as provisional.
- **Racing uses `Substitute` and `Observing`, not analyzers.** Racing is library content, which must not reference `HEAL.HeuristicLib.Analysis`; `LayerDependencyTests` checks this. `Observing` lives in `HEAL.HeuristicLib.Inspection` for that reason.
- **The selected evaluator must be one the contender holds.** A substitution matches its target by reference, and a target it does not reach is an error rather than an observation that never fires. It still finds the evaluator inside the `ApplyingIterationUpdates()` wrapper. When the builder places analyzers on the evaluator, `EvaluatorSelector` must return the analyzed evaluator that the contender holds.
- **Racing applies iteration updates itself.** Under `AfterEachIteration`, the race's epoch ends only when a contender applies pending updates. Racing therefore wraps every tracked contender, and a second wrapper finds nothing pending. Keep that wrapper when a restart rebuilds the tracked graph. The branch's `IterationUpdates_FinishEveryBatchOfTheGenerationBeforeChangingEpoch` checks that every batch of a generation scores in one epoch, so port it.
- **The objective comes from the bound problem (D151 to D155).** A problem's objective is fixed for the lifetime of the problem object (D18). An operator that needs another objective is resolved under a problem with that objective.
- **Per-part random streams change the composite's draws.** Forking the generator per part in `CompositeSearchSpace` changes every meta-creator and meta-mutator sequence, so tests that pin seeded outcomes may need new expected values.
- **Results belong to the run.** A run has one result table shared by all its scopes, so analyzers placed inside the builder collect every contender's observations into one result.

## Open points

These need a decision before the code that depends on them is ported. Under `AGENTS.md`, the architectural ones need the developer's explicit agreement.

1. **Forking and retaining prepared state (architectural).** The racing branch's core change is forking the incumbent's prepared state into challengers (`CreateForkedScope`, `ExecutionFactory.Forkable`) and retaining it across races (`WithContext`). Its tests are `DynamicRateMutator_ForkPreservesIndependentResponseState`, `DynamicRateMutator_ForkRebuildsNonForkableChooseOneComposite`, `ExecutionFactoryResolutionTests.Forking` and `PreparedStateForkingSpecs`. This branch has no counterpart. The [inspection below](#fork-compatibility-inspection) lists what any design must respect.
   - Recommendation: express retention with existing mechanisms first. An entry that keeps one child scope across races and resolves its new tracked graph there gets the same executors for unchanged configurations. A new tracked graph means new wrappers, though, so check which executors that keeps.
   - Bring the challenger copy to the developer as a design question. Copying an executor means copying its data and rebinding its children, which is a snapshot contract no executor has today.
2. **Best-before-change publication on read.** The branch publishes a completed epoch when a result is read, without another evaluation, by reading the live epoch (`branch:…/BestBeforeChangePerformanceAnalyzer.cs:115-121`). ## Fork compatibility inspection

This is a source inspection of `origin/dynamic-Racing` at `c35ebf82` against `core-simplification` at `a1f04a0e`, not a merged or executed test. It claims no compatibility and implements no fork.

**What the branch's mechanism does.**

- `ResolutionScope.CreateForkedScope()` calls `State.Fork()`. That call rejects construction in progress, creates a peer state with the same ancestor, and copies only the local factories whose target implements `IForkableFactoryPreparation`, each delegate once. Other factories and advice factories are prepared afresh, and ancestor state stays shared.
- `ExecutionFactory.Forkable(state, copy, bind)` separates persistent state from execution: the copy function copies the state, and the bind function builds fresh executions and resolves fresh children. For example, `DynamicRateMutator` copies `SourceProblem`, `LastObservedEpoch` and `RemainingResponseCalls`, then binds a new child mutator.
- `WithContext(context)` keeps the prepared state while replacing the aspects used by later resolutions. Racing's `Entry.Restart` uses it before placing the new race's performance callback.

**What the scope holds now.** A [`ResolutionScope`](../src/HeuristicLib/Execution/ResolutionScope.cs) is a node holding:

- its parent;
- a table of executors and other execution nodes, keyed by the configuration and problem reference pair;
- the set of configurations it shares;
- a record of what it or its descendants resolved, for the sharing guard.

The tree holds one run's `RunResults`, the construction lock and the failure state. There are no prepared factories, no aspects or advice, no observation context and no `State` object. Configurations build their executors directly in `CreateExecutor`.

**Consequences for a fork.**

- Only executors remain to copy. An executor owns its private data, its resolved children, its bound problem and any observation wrappers in its graph. Copying table entries would share mutable fields and keep the original children; building replacements loses learned state. A fork therefore needs an executor snapshot contract that copies data and rebinds children. That is an architectural change, not merge work.
- There is no context to swap. Observation is part of the configuration graph, so observing differently means resolving a different graph, which builds new executors for every changed node. Changing a graph never rebinds an existing executor or its callback. This branch's racing resolves its one tracked graph per restart in a new child scope for exactly this reason.
- Problem binding (D5) keys executors by problem reference. A copied executor bound to the same dynamic problem object shares that object's changing environment, which is intended. Copying problem objects would need its own policy.
- A run has one `RunResults` for its whole scope tree, and results of result-producing configurations live in the root's table. A peer fork inside one tree would share the run's results, so challengers' observations land in the same traces. A root fork would need an explicit result-ownership decision: copying live entries or a `RunResults` reference would couple independent runs.
- Sharing must keep its guard (D29): sharing a configuration that a scope or one of its descendants has already resolved, or is building, is an error. A shared executor lives in its owner's table and is built in a child scope of its own.
- Signature checks stay on every typed `Resolve` (D61), including contenders created by `AlgBuilder`. Declared-child preflight and `ChildExecution` mappings stay as they are. A construction failure still ends the whole tree (D62). Elapsed time is measured only through a run (D63).
- The branch's rule to fork only between invocations remains necessary for any design.

The executor table, parent links and sharing ownership are usable foundations. Factory snapshots and context rebinding cannot be merged mechanically, because the factories and contexts they operate on no longer exist.
