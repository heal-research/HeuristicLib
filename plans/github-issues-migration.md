## Agreed migration procedure

- Select one concrete problem, feature request or necessary design repair at a time. Do not turn speculative ideas, generic audits or settled history into work merely to preserve an entry.
- Draft the issue in chat. Keep descriptions very concise: the concrete problem or goal, indispensable context and a short completion outcome. Leave unsettled design details open.
- Obtain explicit approval for every public GitHub change, including creation, edits, comments, labels, closure, PR actions and pushes. Approval applies to the specific action and text discussed.
- Keep useful context in the issue itself. Omit decision dates and links to backlog or plan files. Retain repository artifacts only when they support the work.
- After an approved issue is created, verify its description and record its destination here before removing the migrated source and repairing references. Account for uncommitted source changes as well as committed content.
- Do not implement underlying features as part of this migration. Architectural changes still require accepted scope and design.

## Accepted issue workflow

GitHub Issues are the default home for concrete bugs, feature requests and design repairs. The description holds the current understanding, accepted scope, open questions and completion outcome. Discussion and significant decisions stay with the owning issue; summarize settled discussion back into its description when approved. Search relevant open and closed issues and current architecture guidance before revisiting a design.

A parent issue owns the shared outcome and decisions. Create child issues when selected deliverables need independent review or completion states. An issue does not itself approve implementation or extend earlier architectural acceptance.

Current contracts, terminology and contributor rules stay in repository documentation. Examples, tests and reproducibility artifacts stay in the repository. No mandatory specification layer, ADR framework or planning tool is introduced.

Implementation issues identify their integration destination and close only after their completion and validation criteria are met there. Investigation issues can close after their decision and concrete follow-up work are recorded. Parent issues close when their shared outcome is satisfied.
